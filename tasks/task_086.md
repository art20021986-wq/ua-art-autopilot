## Единственный источник истины

1. Источник этапа, публикации и счётчиков — одна актуальная строка `cars` в
   `crm.db` и её поле `status`; HTML не является источником данных.
2. Один автомобиль может принадлежать ровно одному публичному этапу:
   `korea`, `more`, `gruzia` или `kiev`.
3. Счётчики не изменять арифметически `+1/-1`. После каждого перехода их нужно
   заново вычислять по множеству уникальных опубликованных карточек CRM:

   - `all` — число уникальных `auto_number` с `published=1`;
   - `korea` — только этап 1;
   - `more` — только этап 2;
   - `gruzia` — только этап 3;
   - `kiev` — только этап 4.

4. Обязательный инвариант:
   `all = korea + more + gruzia + kiev`, дублей `auto_number` нет.
5. Оба каталога `/video/katalog.html` и `/site/katalog.html`, карточки этапов и
   верхние chips/counters должны строиться из одного и того же snapshot CRM.

## Постоянный переход этапа для всех карточек

Установить один общий `stage_transition`-контракт для текущих и будущих
`UA-[0-9]{4,}`:

1. CRM handler передаёт `card_id`, целевой канонический status и actor в один
   транзакционный writer.
2. Writer ставит глобальный production lock, читает preimage, проверяет
   допустимость перехода и короткой DB-транзакцией сохраняет этап и совместимый
   payload.
3. После DB commit выполняется один синхронный publisher: primary,
   diagnostic/placeholder, `/video/katalog.html`, `/site/katalog.html`.
4. Publisher пересчитывает категории и все пять счётчиков из свежего snapshot,
   выполняет atomic replace и byte read-back.
5. Success разрешён только после проверки CRM → карточка → оба каталога →
   chips/counters. Fire-and-forget и ложный текст успеха запрещены.
6. При любом DB, renderer, publisher, read-back, HTTP или delayed-check FAIL:
   compensating DB rollback + точное восстановление файлов + проверка rollback.
7. Повтор той же команды идемпотентен: дубль не создаётся, счётчики не дрейфуют,
   данные и media не меняются.
8. Legacy writers и прямой SQL не должны оставлять один `auto_number` в двух
   категориях; после следующей проверенной публикации catalog guard обязан
   восстановить каноническое распределение.
9. Runtime LLM tokens = 0.
