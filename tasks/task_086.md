# TASK 086 — UA-0011-KOREA-STAGE-CARD-COUNTER-SYNC-006 v2.0

## Исправление целевого этапа по прямой команде владельца

Дата: 29.08.2026.

Дословная цель текущей команды владельца: «Одиннадцатая карта. Статус Кореи.
Удали её с Киева. Сделай полноценную карточку, как обычно, со статусом Кореи,
с информацией, с главной фотографией. Также в Корее измени цифру на такую,
которая должна быть».

Предыдущая редакция TASK 086 ошибочно зафиксировала этап «На пароме» и
отменяется до production. Актуальная и единственная цель:

- `UA-0011.status='kr_bought'`;
- публичная категория `korea`;
- публичная подпись «В Корее» / «У Кореї»;
- в `more`, `gruzia` и `kiev` карточка отсутствует;
- морской, грузинский и киевский payload, несовместимый с этапом Кореи,
  очищается транзакционно;
- существующие данные автомобиля и весь media manifest сохраняются.

Эта команда является отдельным письменным bounded production authorization.
Дополнительное подтверждение владельца не требуется. При техническом зависании
разрешён один последовательный безопасный автоповтор. Два writer-процесса
одновременно запрещены.

## Единственный источник истины

1. Источник этапа — ровно одна строка `cars` в `crm.db`, поле `status`.
2. Один опубликованный `auto_number` принадлежит ровно одному публичному
   этапу: `korea`, `more`, `gruzia` или `kiev`.
3. HTML не является источником данных. Обе карточки и оба каталога строятся из
   одного свежего snapshot CRM.
4. Все пять chips пересчитываются по множеству уникальных опубликованных
   `auto_number`, без арифметических `+1/-1`:
   `all`, `korea`, `more`, `gruzia`, `kiev`.
5. Обязательный инвариант:
   `all = korea + more + gruzia + kiev`; дублей `auto_number` нет.

## Постоянный перекрёстный контроль

Ввести общий stage-payload контракт для текущих и будущих карточек:

1. Все смены этапа проходят через один транзакционный writer под глобальным
   production lock.
2. На реальном переходе очищаются только поля, несовместимые с новым этапом.
3. SQLite triggers страхуют legacy/direct SQL от сохранения payload другого
   этапа.
4. Public projection никогда не показывает payload другого этапа, даже до
   следующей публикации.
5. Publisher синхронно обновляет primary, diagnostic/placeholder,
   `/video/katalog.html` и `/site/katalog.html`, пересчитывает категории и
   chips из одного snapshot и делает byte read-back.
6. Success разрешён только после цепочки
   CRM → карточка → оба каталога → категории → chips/counters.
7. Любой FAIL вызывает compensating DB rollback, точное восстановление файлов
   и проверку rollback.
8. Повтор команды идемпотентен: карточка не дублируется, chips не дрейфуют,
   media и бизнес-данные не меняются.
9. Runtime LLM tokens = 0.
