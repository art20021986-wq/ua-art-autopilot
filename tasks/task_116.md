# TASK116 — защита спецификаций и восстановление публикации

**Контракт:** `UA-ART-CRM-SPEC-PUBLISH-RECOVERY-001`  
**Версия:** 1.0  
**Дата:** 2026-09-07  
**Состояние:** execution candidate подготовлен локально; Remote Gate A и Gate B не выполнены; Production закрыт.

## Исходный дефект

При попытке разместить `UA-0017` CRM вернула
`BASE_PUBLISH_FAILED:UA-0017` с причиной
`UA115_ADDITIONAL_SPEC_INCOMPLETE:UA-0017:0:0`, затем выполнила полный
откат. Следующее сообщение CRM указало, что страницы сайта отстали от базы.
Следовательно, этот запуск `UA-0017` завершился отказом и откатом. Актуальное
Production-состояние карточки остаётся `UNKNOWN_REMOTE_NOT_OBSERVED`: успешная
публикация не подтверждена, а удалённое состояние в этой работе не читалось.

## Неподвижные ограничения

- Работа ведётся только в отдельной ветке и изолированном Preview/Sandbox.
- Candidate ведётся только в отдельной ветке
  `codex/ua-art-crm-spec-publish-recovery-001`; branch/head подтверждаются
  GitHub evidence. Production-root `/home/Carix` не используется как
  доказательство ветки.
- Production, сервисы, DNS, базы, публичные страницы и публикационный флаг не
  изменять до проверенного Gate B и отдельной команды владельца.
- Не менять существующие VIN, цены, медиа, описания, URL, дизайн, этапы,
  контейнерные данные, основную или дополнительную спецификацию попутно.
- Не внедрять рекламу, сторонние виджеты или внешние ссылки вокруг VIN и
  спецификаций.
- Локальный PASS или Preview PASS не является Gate B и не разрешает Production.

## Этап A — BEFORE, границы и воспроизводимость

1. На удалённом контуре выполнить только read-only `remote_gate_a.py`.
2. Зафиксировать фактические пути двух публикуемых корней, базы CRM и базы
   спецификаций; точные версии runtime-файлов; UID/VIN-привязку `UA-0017`;
   текущий `published`; наличие карточки, диагностики и ровно одной ссылки в
   каталоге.
3. Зафиксировать отдельную ветку и commit через GitHub branch/commit/PR evidence.
   Строка `BASE_SHA` внутри candidate-кода и возможные данные `/home/Carix`
   являются наблюдением, а не доказательством GitHub commit.
4. Сформировать BEFORE-манифест на стороне изолированного Gate B-контура. В
   Production этот этап не выполняет запись и не создаёт backup-файлы.

## Этап B — неизменяемая дополнительная спецификация

1. Хранить спецификацию версиями `CANDIDATE -> ACTIVE -> ARCHIVED`; активна не
   более чем одна ревизия на `UID + VIN`.
2. Новая пустая, неполная, неподтверждённая или относящаяся к другому VIN
   ревизия не может стереть последнюю валидную ACTIVE-ревизию.
3. Публичная готовность: не менее 10 видимых подтверждённых строк, совпадение
   UID, SHA-256 VIN, digest ревизии и фактического HTML-содержимого.
4. Любое создание карточки, изменение CRM, повторная сборка, Preview или
   публикация обязаны сохранять активные спецификации всех старых и новых
   карточек. Изменения вне точного набора артефактов целевой карточки блокируют
   сборку как `SITE_FOUNDATION_CHANGED`.
5. При недоступности источников оставить предыдущую ACTIVE-версию и перевести
   новый кандидат в `NEEDS_REVIEW/REJECTED`; пустой блок не публиковать.

## Этап C — основная спецификация после сохранения VIN

1. Сохранение валидного VIN идемпотентно запускает подготовку именно этой
   карточки, не ожидая общей очереди.
2. Автоматически заполнять только пустые allowlist-поля основной спецификации:
   марка, модель, год, комплектация, кузов, топливо, двигатель/объём, коробка и
   привод.
3. Уже заполненные оператором значения не перезаписывать. Каждая запись
   проходит compare-and-swap по исходному digest строки и получает provenance.
   При смене VIN автоматически вернуть только неизменённые системные значения
   прежнего VIN и заполнить их заново; ручные правки сохранить.
4. Пробег и цвет нельзя достоверно получить из VIN. Их можно заполнять только
   из подтверждённой записи конкретного автомобиля (аукцион, тот же VIN в CRM)
   либо вручную; отсутствие этих данных не подменять догадкой.
5. Ошибка декодера не откатывает сохранённый VIN и не публикует карточку. CRM
   показывает точный статус подготовки и возможность безопасного повтора.

## Этап D — удаление дублей этапов CRM

С новых клавиатур скрыть, но не удалять из истории/схемы:

- `kr_bought` — «Выкуплено, на нашей парковке»;
- `sea_loaded` — «Загружено в контейнер»;
- `sea_transit` — «В пути»;
- `ua_handed` — «Передано клиенту».

Старые Telegram callback должны получать ACK и fail-closed ответ с предложением
выбрать актуальный этап; данные карточки не менять. Канонические состояния:
Корея, На пароме, Грузия, Киев, Продано, Архив. «Номер и дата контейнера»
остаётся отдельным действием, не статусом. Любая последующая миграция старых
значений выполняется только через отдельный dry-run: `В пути` неоднозначен, а
«загружено» ещё не доказывает выход судна.

## Этап E — восстановление публикации и защита аналогичных карточек

1. Перед публикацией проверить точную привязку `UID + VIN`, получив VIN
   `UA-0017` только из CRM, а также здоровье worker, ACTIVE-ревизию и минимум
   10 видимых строк. Текущий VIN `UA-0017` в этом пакете не заявляется.
2. Preview строго не вызывает legacy publisher и собирается в версионном
   изолированном каталоге.
3. Production adapter должен принимать только два точных корня, общий lock,
   свежий target/root/build-bound Gate B receipt и отдельную команду владельца.
4. Допустимый scope одной публикации: карточка `UA-0017`, её диагностика,
   `katalog.html` и `index.html`. Любое иное изменение вызывает полный откат.
5. После сборки проверить UID/VIN, фактические строки спецификации, digest,
   отсутствие generic fallback, одну точную ссылку каталога, сохранность
   листинга и идентичность двух корней.
6. CRM устанавливает `published=1` только после подтверждённого успеха. При
   исключении или отрицательном результате вернуть/оставить `published=0` и
   показать оператору конкретную причину.

## Этап F — Gate B, выпуск и контроль

1. На свежих копиях удалённого состояния применить candidate и выполнить
   матрицу A–E, включая повторный запуск, stale callback, сбой источника,
   конфликт VIN, рассинхронизацию корней и принудительный rollback.
2. Gate B считается проверенным только при наличии свежего отчёта, привязанного
   к GitHub-verified branch/commit, target UID, exact CRM VIN hash, revision digest, двум
   root fingerprints и candidate code digest.
3. До такого отчёта выпуск `UA-0017` имеет статус `BLOCKED`, а её текущее
   Production-состояние — `UNKNOWN_REMOTE_NOT_OBSERVED`.
4. После Gate B владелец должен отдельно прислать точную команду:

   `ПУБЛИКОВАТЬ UA-0017`

   Ранее данное «утверждаю ТЗ/в работу» этой командой не является.
5. После разрешения: одна canary-публикация, постпроверка CRM/сайта, отчёт и
   отдельное сообщение о завершении. Другие карточки автоматически не выпускать.

## Риски и меры

| Риск | Защита |
|---|---|
| Пустая спецификация стирает рабочую | Неизменяемые ревизии; fail-closed activation |
| VIN заполняет не ту карточку | Точная UID/VIN-привязка, hash и CAS |
| Автозаполнение портит ручные данные | Только empty-only allowlist + provenance |
| Старые Telegram-кнопки меняют статус | Ранний legacy callback blocker; schema/history сохранены |
| CRM считает неудачную публикацию успешной | `published=1` только после валидированного publisher result |
| Сборщик меняет старые карточки/дизайн | BEFORE/AFTER manifest и exact-path allowlist |
| Два web-root расходятся | Двойная проверка и обязательный rollback |
| SIGKILL прерывает in-memory rollback | До выпуска нужен внешний восстановимый snapshot платформы |
| Локальные тесты ошибочно объявлены Gate B | Отдельные статусы LOCAL, REMOTE GATE A и GATE B |
| Ошибочно заявлены ветка/commit | Только GitHub evidence; `/home/Carix` не источник доказательства |

## Rollback

- До Production изменений нет: rollback не требуется.
- Gate B выполняется только на восстановимых копиях; повторный прогон должен
  быть идемпотентным.
- Production-выпуск требует внешнего BEFORE snapshot и полного манифеста двух
  корней и БД. Внутренний atomic rollback покрывает обычные исключения и
  validation failure, но не заменяет внешний snapshot при аварийном завершении
  процесса.
- Откат восстанавливает только изменённые TASK116-артефакты и не должен удалять
  новые пользовательские данные, появившиеся после снимка.

## Definition of Done

- Дополнительная спецификация сохраняется на старых и новых карточках при всех
  проверяемых несвязанных изменениях.
- Валидный VIN запускает empty-only заполнение основной спецификации; ручные
  значения сохранены.
- Четыре legacy-кнопки отсутствуют в новых клавиатурах, старые callbacks ничего
  не меняют и не падают.
- Неудачная публикация не оставляет `published=1` и не меняет старые страницы.
- На Gate B-копии `UA-0017` собирается и откатывается без изменений вне scope.
- Verified Gate B report существует; Production changes до команды владельца —
  `0`; после точной команды canary и постпроверка подтверждены.
