## 1. Цель

Создать в CRM отдельный полноценный процесс обработки заявок «Авто под заказ», поступающих с сайта и из клиентского Telegram-бота.

Каждая заявка должна:

1. поступать в CRM автоматически;
2. создаваться ровно один раз;
3. содержать минимум данных, достаточный для связи и предварительного расчёта доставки;
4. сохранять выбранную страну покупки, модель, бюджет и город доставки;
5. проходить понятные этапы обработки;
6. при подтверждении заказа связываться с клиентом и будущей карточкой автомобиля;
7. не создавать пустую публичную карточку автомобиля до фактической покупки машины;
8. не изменять существующие 16 карточек, CRM-данные автомобилей, медиа, бот и каталог.

## 2. Результат аудита текущего состояния

### 2.1. Что уже существует

В действующей CRM есть таблица clients со следующими основными полями:

- name;
- phone;
- telegram;
- whatsapp;
- car_interest;
- budget;
- wishes;
- source;
- prepayment;
- stage;
- responsible;
- next_contact;
- tg_user_id;
- review_status;
- created_at и updated_at.

Это достаточная база для хранения контакта клиента, но недостаточная для отдельной заявки «Авто под заказ».

В CRM уже есть раздел «Заявки из бота», однако он читает упрощённый список visits.all_leads(). Полноценные карточки клиентов хранятся отдельно в clients. Таким образом, сейчас существуют два параллельных контура:

1. упрощённые заявки/аналитика клиентского бота;
2. полноценные карточки клиентов CRM.

Единого гарантированного объекта заявки между ними нет.

### 2.2. Выявленные недостатки

1. Нет отдельной сущности «Заявка на авто под заказ».
2. Один клиент не может корректно хранить несколько разных запросов без перезаписи car_interest, budget и wishes.
3. В заявке нет обязательных полей «страна доставки» и «город доставки».
4. Нет отдельного стабильного поля страны покупки автомобиля.
5. Страна покупки Грузия может быть ошибочно смешана с логистическим этапом «В Грузии».
6. Нет общего request_id и уникального ключа, защищающего от повторной записи при двойном нажатии или повторной доставке Telegram-события.
7. Не зафиксирован единый язык заявки uk, ru или ka.
8. Не зафиксированы источник страницы, URL и рекламные метки.
9. Заявка из списка visits не гарантированно превращается в карточку клиента CRM.
10. Аналитика может считать заявку отдельно от созданного клиента.
11. Нет безопасного процесса «заявка → договорённость → задаток → заказ → купленный автомобиль».
12. Нет отдельного контроля просроченного первого контакта.

## 3. Архитектурное решение

Не хранить каждую новую заявку непосредственно в одной строке clients.

Использовать две связанные сущности:

1. clients — один человек и его контактные данные;
2. order_requests — одна конкретная заявка этого человека на подбор автомобиля.

Связь:

один client может иметь несколько order_requests.

Таблица cars остаётся отдельной. Она не используется для сырой заявки. Связь с cars создаётся только после фактического подтверждения заказа и покупки автомобиля.

Главный источник истины новых заявок — order_requests.

## 7. Защита от дублей

1. Перед отправкой сайт/бот создаёт request_id.
2. Повторное нажатие отправляет тот же request_id.
3. В CRM действует UNIQUE request_id.
4. Для Telegram дополнительно использовать source_event_id вида chat_id:message_id или WebApp query_id.
5. Повторная доставка события возвращает существующую заявку, а не создаёт новую.
6. Клиент определяется:
   - сначала по tg_user_id;
   - затем по нормализованному телефону/WhatsApp;
   - если совпадения нет — создаётся новый client.
7. Совпавший клиент не означает совпавшую заявку: один клиент может заказать несколько разных автомобилей.
8. В аудит записывать DUPLICATE_BLOCKED без создания второй строки.

## 8. Этапы работы заявки

Использовать отдельный статус заявки, не логистический этап автомобиля:

1. new — новая;
2. clarification — уточняем запрос;
3. calculation — делаем расчёт;
4. offer_sent — предложение отправлено;
5. negotiation — согласование;
6. deposit_expected — ожидается задаток;
7. deposit_received — задаток 500 USD получен;
8. searching — поиск/торги;
9. purchased — автомобиль куплен;
10. logistics — связан с карточкой купленного авто;
11. completed — выполнено;
12. lost — отказ/неактуально;
13. duplicate — технический дубль, не рабочая заявка;
14. spam — спам.

Запрещено использовать для заявки статусы «В Корее», «На пароме», «В Грузии», «В Киеве». Это статусы конкретного купленного автомобиля.

## 10. Переход заявки в автомобиль

### 10.1. До задатка

Не создавать строку в cars и не показывать запрос в публичном каталоге.

### 10.2. После задатка

Допускается создать внутренний заказ, связанный с order_request и client, но published=0.

### 10.3. После фактической покупки

Кнопка «Создать карточку купленного автомобиля»:

1. создаёт черновик cars;
2. сохраняет client_id и order_request_id;
3. переносит только подтверждённые модель/бюджет/пожелания;
4. не придумывает VIN, цену, год, пробег и этап;
5. published=0;
6. требует обычного валидатора карточки;
7. не публикует автомобиль автоматически.

Публикация возможна только после заполнения обязательных автомобильных данных и отдельного подтверждения.

## 12. Аналитика

Отдельно считать:

- уникальные заявки, не клики;
- заявки по стране покупки;
- заявки по модели;
- заявки по стране/городу доставки;
- источники;
- язык;
- конверсию new → calculation → offer_sent → deposit_received → purchased;
- время первого ответа;
- потерянные заявки и причина;
- выручку/результат только после связи с реальным автомобилем.

Legacy visits.all_leads не удалять. После проверки сделать совместимый адаптер или безопасный импорт с отдельным manifest и дедупликацией.

4. Свободный текст экранировать.
5. Параметры стран/языков/status проверять по whitelist.
6. Доступ к заявкам только для авторизованных сотрудников CRM.
7. Все изменения — через существующий audit.
8. Согласие на обработку контакта фиксировать consent_at.
9. Не отправлять CRM/контактные данные в внешние сервисы перевода.

## 14. Миграция и откат

До изменений:

1. резервная копия crm.db;
2. PRAGMA quick_check;
3. экспорт структуры clients;
4. количество строк clients и visits leads;
5. SHA-256 базы;
6. отдельная Sandbox-копия базы.

Миграция:

- только ADD COLUMN/CREATE TABLE/CREATE INDEX;
- никаких DROP/RENAME;
- идемпотентная;
- короткие транзакции;
- busy_timeout;
- версия схемы;
- тест сначала на копии.

Откат:

- код переключается на старый read-only путь;
- новая таблица остаётся неиспользуемой либо восстанавливается backup;
- существующие clients/cars не меняются;
- рестарт только при отдельном Gate B.

## 16. Definition of Done

Задача выполнена только при одновременном PASS:

- новая сущность order_requests работает;
- существующая clients сохранена;
- единый контракт сайта и бота;
- минимальные поля имя/контакт/страна и город доставки присутствуют;
- 8 стран;
- одна отправка = одна заявка;
- заявка видна CRM и менеджеру;
- этапы заявки отделены от этапов автомобиля;
- заявка не создаёт публичный автомобиль;
- конвертация в автомобиль только после подтверждённого заказа;
- audit работает;
- миграция/rollback протестированы;
- старые заявки доступны;
- CRM/bot не зависают;
- 16/16 карточек неизменны;
- UA-0009 SAFE CHECK PASS;
- Production выполняется только после отдельного письменного разрешения.
