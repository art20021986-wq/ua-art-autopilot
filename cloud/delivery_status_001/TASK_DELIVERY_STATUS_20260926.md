# UA-ART-DELIVERY-STATUS-001 — принято к исполнению

## Цель

На границе CRM/Webhook → публикация отображать только четыре статуса: `korea` «В Корее», `ferry` «На пароме», `georgia` «В Грузии», `kyiv` «В Киеве». Для любого иного значения публичная проекция `hidden`: карточка не попадает в каталог, табы и публичные счётчики. Запрещены «Продано в пути», «Выехало в Киев», «Продано», «Архив» и внутренние коды этих этапов.

## Фактическая архитектура и границы

- Из известных исходников CRM внутренние активные коды: `kr_bought`, `sea_loaded`, `ge_waiting`, `ua_arrived`. Публичные `korea/ferry/georgia/kyiv` — отдельная проекция; прямое изменение всех строк CRM в эти четыре значения может сломать callback и этапы бота.
- Рабочие `cars_ui.py`, `cars_schema.py`, `db.py`, генераторы `stranica.py`/`master_card.py`, действующая схема `crm.db` находятся на PythonAnywhere; в доступном репозитории есть установщики и частичные снимки, но нет подтверждённой полной текущей версии этих исходников.
- По `cloud/latest_status.md` параллельная задача согласования CRM и сайта не установлена и ожидает сброса квоты CPU. Перед любой установкой проверить текущие процессы, код, базу и блокировку писателей; не совмещать две транзакции.

## Реализация

1. Сохранить текущие четыре активных внутренних кода в базе CRM. Установить `delivery_status.py` как единственную функцию проекции на выходе webhook/публикации и при формировании каталога. Не заменять логику внутренних этапов бота без отдельного контракта.
2. В обработчике событий после сохранения статуса вычислять `public_status`. Если результат `hidden`, не генерировать публичную карточку, убрать её из индексируемого каталога в пределах существующего транзакционного механизма и исключить из счётчиков. Существующее значение `published` и жизненный цикл проданной карточки согласовать с текущим кодом удаления; не удалять медиа/строки из CRM.
3. Табы и общий счётчик должны считаться по одному набору опубликованных карточек после проекции, без подстановки последнего известного статуса. Публичные подписи берутся только из `public_label`; отсутствие подписи означает отсутствие карточки в UI.
4. Перед SQL проверить фактические `cars.status`, распределение значений, внешние связи, триггеры, активных писателей и полную резервную копию SQLite с WAL. `migrate_removed_statuses.sql` выполнить один раз под штатной блокировкой. Если схема или значение отличается — остановить, а не подменять SQL догадками.
5. Пересобрать затронутые страницы штатным публикователем, проверить обе публичные точки выдачи, Safari/Chrome и CDN/кэш. Из CRM записать по одному тестовому переходу каждого активного этапа; сравнить БД → webhook → HTML → вкладка/счётчик. Запрещённый и неизвестный статус должен давать `hidden` без HTTP 500.

## Условия приёмки

- Для 4 активных внутренних кодов подтверждены соответствующие 4 публичных статуса; других публичных статусов нет.
- Для запрещённых/неизвестных/нестроковых значений нет 500, публичной карточки и прибавки счётчика.
- Миграция идемпотентна; не затрагивает активные статусы, цены, VIN, фото, опубликованные данные иных автомобилей.
- Число карточек в каждом табе равно числу реально видимых карточек этого этапа; сумма четырёх табов равна общему числу.
- Есть резервная копия, идентификатор версии, контрольные суммы до/после, квитанция установки и проверенный откат.

## Текущий статус

Кандидат и локальные тесты подготовлены. Интеграция с рабочими исходниками, production Gate B, SQL на рабочей базе и публичная проверка не выполнены. Не объявлять задачу завершённой до получения живых исходников и прохождения условий приёмки.
