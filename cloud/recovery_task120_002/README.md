## Что исправляет эта подготовка

В текущем control-plane есть аварийная остановка после TASK120, но нет штатной команды её контролируемого завершения. Watchdog работает с незавершёнными транзакциями и сам устанавливает HALT после восстановления. Сейчас все шесть транзакций завершены; ожидание watchdog не снимает остановку.

Контроллер проверяет конкретные task/run/epoch/request и свидетельство `ABORTED_NO_PRODUCTION_WRITE`, исходные байты HALT, 18 закреплённых runtime-файлов, девять workflow, все claims/transactions/launch/nonce/consumed records и свежий снимок Actions. Он не объявляет TASK120 успешным rollback: установка и откат тогда не выполнялись.

Обработка errno 22 и восстановление спецификации находятся в отдельном [PR #79](https://github.com/art20021986-wq/ua-art-autopilot/pull/79). Подтверждённый там серверный результат v7 — 182/182 PASS; это не завершённый Gate B по всему сайту. Текущий recovery PR не повторяет публикацию карточек и не выдаёт снятие HALT за восстановление спецификации.

План проверяет **замороженный снимок подготовки**: main `2ce0c3a886f124c5865c564a7073ef1805861f1c`, tree `6f9914b2f742ff4fb4001a5046f86408ad4ecc65`. Согласованная подмена файла и его записи inventory либо сокрытие claim не проходят. Контроллер не утверждает, что офлайн-копия является live main.

Снимок Actions допускается не старше 600 секунд. План имеет срок 5 минут и служит свидетельством подготовки после его истечения, а не постоянным разрешением. После изменения main требуется свежая проверка. Будущий штатный runner должен получать текущий commit/tree из доверенного Git/API и связывать их с отдельным планом; циклическое обновление константы main при каждом слиянии не является схемой активации.

## Ровно три операции будущего перехода

1. Удалить `state/AUTOPILOT_HALT.json` только с исходным SHA-256 `35c8f42ec20d33f259cbf87aaaa193c86c4d5ae469fa4a8e67e6d049ce0091e9`.
2. Добавить исходные байты в `state/halt_history/UA-ART-RECOVERY-TASK120-002/halt.json` без перезаписи существующего файла.
3. Добавить связанный receipt в `state/halt_history/UA-ART-RECOVERY-TASK120-002/receipt.json` без перезаписи истории.

Все три изменения должны появиться в одном commit и одном атомарном обновлении ref по ожидаемому исходному commit. До этого HALT остаётся действующим. Дрейф ref отклоняет переход. После потери ответа результат сверяется; второй переход не выполняется.

Эта атомарность **доказана только в новом локальном bare Git**, без remote, унаследованных credentials, hooks и перенаправления Git. Все approvals/receipts репетиции помечены `LOCAL_REHEARSAL_ONLY` и не являются разрешением владельца на production. Локальная модель имеет отдельный plan hash; отчёт явно отличает его от хеша плана контроллера. Копия сохраняет содержимое исходных файлов; режимы файлов рабочего полного Git-дерева должны дополнительно сохраняться настоящим runner.

Команда `controller.py execute` всегда отказывает до чтения аргументов исполнения и записи. Флагом или синтетическим JSON включить рабочий переход нельзя. Права, активные YAML, текущий runtime manifest, mode и историческое approval этим PR не меняются.

## Воспроизведение подготовки

Нужен изолированный checkout указанного исходного commit и эта папка с подготовленным кодом. Для dry-run нужен заново полученный полный снимок пяти статусов Actions, привязанный к той же версии main. Сохранённый просроченный снимок нельзя выдавать за свежий. Команды ниже запускаются из корня такой копии; `--output` должен быть новым файлом непосредственно в каталоге evidence.

```bash
python -m unittest discover -s cloud/recovery_task120_002/tests -v
python cloud/recovery_task120_002/controller.py dry-run \
  --root "$PWD" \
  --inventory "$PWD/cloud/recovery_task120_002/evidence/source-inventory.json" \
  --queue "$PWD/cloud/recovery_task120_002/evidence/queue-review.json" \
  --output "$PWD/cloud/recovery_task120_002/evidence/new-dry-run.json"
python cloud/recovery_task120_002/rehearse_snapshot.py \
  --root "$PWD" \
  --inventory "$PWD/cloud/recovery_task120_002/evidence/source-inventory.json" \
  --queue "$PWD/cloud/recovery_task120_002/evidence/queue-review.json" \
  --output "$PWD/cloud/recovery_task120_002/evidence/new-snapshot-rehearsal.json"
```

Тесты используют временные копии и историческое время наблюдения как fixture; они не продлевают актуальность отчёта очереди. Репетиция создаёт собственный временный Git и удаляет его после проверки. Рабочие данные, действующий HALT и 115 исходных файлов не изменяются.

## Следующий шаг и общая задача сайта

Подготовка штатного маршрута входит в уже утверждённое ТЗ. Для неё повторное согласование подготовки не требуется. Его активацию и сам управляющий переход нельзя подменить ручным удалением HALT: нужен проверенный diff существующих policy/runtime/authority bindings, реальная группа `ua-art-production-writer`, свежая очередь и отдельная команда владельца на конкретный результат.

После завершения этого этапа управления работа продолжается по SPEC-AUTO-10-RESTORE-001: спецификация на всех существующих и новых карточках, один VIN, сохранение оболочки и проверенные циклы добавления/изменения/удаления. Карточки 17 и 18 не публикуются этим recovery-пакетом. Реальные источники, publisher, жизненный цикл и итоговый Gate B ещё должны быть подтверждены отдельно фактическими проверками.
