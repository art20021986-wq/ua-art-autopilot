## Точное подключение подготовлено

Полностью прочитаны текущие `lead_bot.py`, `client_ui.py`, `team_bot.py` и WSGI.
`integrate.py` проверяет четыре исходных SHA256, формирует приватные копии с
минимальными вставками и diff. Любое расхождение источника останавливает сборку.

```sh
python cloud/order_eight_countries_001/integrate.py --sources /path/to/current/private/sources --output /path/to/new/private/candidate
```

Изменяются только:

1. **lead_bot:** регистрация после `handlers.clear()` и `client_ui.register`,
   перед последним `return app`. Новая группа выбирается раньше всех текущих.
2. **client_ui:** подпись одной кнопки. Все действующие входы `c_order`, `c_ans:`,
   `lead_start`, `buycar:`, `ready`, `custom_order` перехватываются адаптером.
   Старые незавершённые кнопки анкеты открывают новый выбор страны. Переходы
   в каталог, карточку, бронь, вопрос, условия, контакты и главное меню очищают
   только состояние новой анкеты и передают управление действующему экрану.
3. **team_bot:** одна кнопка папки и одна регистрация перед возвратом приложения.
   `who(update)` и активная роль owner/admin/manager проверяются при каждом чтении,
   только в личном чате. Доставка использует существующий CRM job queue и бот,
   действующих менеджеров, при их отсутствии — действующих владельцев.
4. **WSGI:** финальная обёртка только для `/api/orders/`, снаружи аналитики,
   bridge, SEO и актуального `uaart_public_prices_v1`. Прочие маршруты делегируются.

Обработчик старого inbox не вызывается с номером заказа: у него другой тип записи
и callback. Заказ получает собственный `orders:open:<id>`. Уведомления отправляются
после commit; успешная доставка каждому адресату сохраняется отдельно. Ошибка
одного адресата не блокирует остальных и не повторяет уже подтверждённые доставки.
Неоднозначный сетевой сбой допускает повтор с тем же номером. Повторы ошибок имеют
увеличивающийся интервал до одного часа; заявки не удаляются.

`settings.example.json` выключен и не содержит выдуманного согласия или секретов.
Хост читает `/home/Carix/order_requests/settings.json` либо явный `UA_ORDER_SETTINGS`.
Пакет `ua_order` должен быть в существующем пути импорта `/home/Carix`; каталог и
строки задаются точными приватными путями, ресурсы — `/home/Carix/video/order`.
До включения явно инициализируется **только** `Carix$orders`, создаётся
приватный `session.key` (не менее 32 случайных байт) и передаются тексты
согласия uk/ru/ka с версией. В этом выпуске использованы ранее подготовленные
подписи формы; это не отдельная утверждённая политика компании. Runtime сам
не создаёт базу, ключи или миграции.

В текущих проверенных обработчиках ограничитель частоты не найден. Новый небольшой
лимитер использует стандартную библиотеку: 10 web-попыток на сессию/минуту,
60 на серверный REMOTE_ADDR/минуту, 60 Telegram-обновлений на пользователя/минуту.
Каждый лимитер ограничен 4096 активными ключами. Это **лимит одного процесса**,
не глобальный лимит между WSGI workers; он не заменяет уникальность заявки в БД.

Отсутствующая/выключенная конфигурация сохраняет старое поведение. Некорректная
включённая конфигурация блокирует новый приём: API возвращает 503, бот сообщает
о временной недоступности. Существующие сайт, каталог и CRM продолжают работать.

`integrate.py` только готовит патч. Рабочая установка выполнена явно через
`deploy.py`, затем сайт и существующая задача ботов перезапущены штатно через
PythonAnywhere. Автоматического merge или отложенного запуска нет.

Первая команда требует уже используемую PTB в тестовом окружении. При
отсутствии библиотеки интеграционные тесты должны завершиться ошибкой,
а не пропускаться и называться PASS.

Проверены 43 новых Python-теста и пять существующих проверок справочника.
JS-проверки покрывают 24 сочетания страны/языка и сценарии неизвестного
маршрута, сохранения независимых полей и сборки контракта. В их числе:
10 параллельных повторов → одна заявка/одна outbox-строка; повтор после
потери ответа и перезапуска; rollback при ошибке outbox; повтор Telegram
event; чужая квитанция; срок/владение handoff; устаревшее меню; восстановление
квитанции после перезапуска бота; запрет чтения CRM без авторизации.

Отдельная сквозная проверка проходит через HTTP handoff → клиентский адаптер
бота → подтверждение → плоскую папку CRM → детали → outbox. Повтор подтверждения
оставляет одну заявку и одно уведомление; модель, комментарий и контакт сохранены.

Дополнительно проверены реальные группы диспетчера PTB, старые кнопки и выходы
из анкеты, отказ одного получателя, отсутствие повторов успешному получателю,
изоляция ошибки конфигурации, ограничитель и отказ SQLite на сетевой ФС.
