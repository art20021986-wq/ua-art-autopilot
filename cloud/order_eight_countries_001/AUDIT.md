## Текущий клиентский бот: подтверждённая цепочка

27.09.2026 в 10:46:28 UTC получен полный `lead_bot.py` через авторизованное
текстовое представление PythonAnywhere: 100 314 байт, AST PASS, SHA256
`27270e38f1b7ed913140127231149b6d862876f3b3a02a58c4a852b40ce8a3f8`.
Этот SHA также совпадает с protected hash в ранее выполненном серверном
preflight CRM-PHOTO-INTAKE-PREFLIGHT-20260927 от 08:31 UTC. Сам приватный
исходник в публичный репозиторий не включён.

Фактический порядок внутри `build_application`:

1. Создаётся PTB Application и регистрируются прежние диалоги.
2. `app.handlers.clear()` удаляет все эти обработчики.
3. Добавляется временный `/start`.
4. Вызывается `client_ui.register(app, MANAGER_CHAT_ID)`; предусмотрен старый
   вариант вызова без chat_id.
5. Приложение возвращается вызывающему коду.

Новый адаптер подготовлен после шага 4. В текущем client_ui все регистрации
используют группу −1. Новая группа выбирается перед всеми существующими после
завершения их регистрации. Старые jobs очисткой handlers не удаляются; задача
их не меняет.

## Действующий клиентский сценарий

- Главное меню: наличие/в пути, подбор из Кореи, условия, контакты, WhatsApp.
- Подбор: `c_order` → класс → бюджет → срок → `_zayavka` → экран «Заявка принята».
  Нативного выбора восьми стран и моделей с фото здесь ещё нет.
- Старые входы `lead_start`, `buycar:`, `ready`, `custom_order` ведут в тот же
  обработчик. Ответы приходят через `c_ans:`; состояние — `user_data['podbor']`.
- `_zayavka` пытается отправить сообщение владельцу через клиентского бота
  и отдельно отмечает lead в visits. Ошибка отправки ловится и логируется;
  экран успеха показывается независимо. Долговечная квитанция заказа в этом
  обработчике отсутствует. Поведение внутренних функций visits не объявляется
  проверенной системой приёма заказов: их текущие исходники здесь не читались.
- Свободный ввод модели предлагает текст вопроса, но `client_ui.register`
  регистрирует только commands/callbacks. Старый text handler в lead_bot снят
  вызовом handlers.clear. Нельзя считать его действующим обработчиком анкеты.
- Утверждённого согласия и ограничителя новых заявок в этих обработчиках не
  найдено. Ограничители тайминга/heartbeat не являются лимитом приёма заявки.

## Действующий CRM-сценарий

`who(update)` находит активного сотрудника; для владельца предусмотрен ensure_owner.
Меню содержит необработанное, проверку, автомобили, клиентов, поиск, сводку,
сотрудников, журнал и управление ИИ с существующим разграничением ролей.
`show_menu` дополнительно использует прежнюю статистику и debounce; они сохранены.

`notify_managers` обслуживает inbox: сообщение «Новая информация от владельца»,
ссылка `inbox_open:<id>`. `notify_admins_review` обслуживает cars/clients review.
Передавать этим функциям идентификатор отдельного заказа нельзя. Новый адаптер
использует проверенную политику получателей (активные менеджеры, иначе владельцы),
тот же CRM-бот/job queue и callback `orders:open:<id>`.

Все прямые регистрации team_bot находятся в группе 0; импортируемые cars_ui и
ai_filter могут добавлять группы. Поэтому номер новой группы не зашит вручную:
он выбирается перед фактически зарегистрированными группами. Их обработчики
не очищаются и не переставляются.

## Как работает подготовленный кандидат

| Интерфейс | Сценарий |
|---|---|
| Сайт | Страна → пять моделей с фото либо другая модель → параметры/доставка/контакт → проверка данных и согласие → сохранение и номер |
| Клиентский бот | Страна → пять моделей → фото выбранной модели → параметры/доставка/контакт → проверка данных и согласие → сохранение и номер |
| Переход сайт → бот | Проверенный полный черновик хранится 30 минут; случайный идентификатор привязывается к первому проверенному Telegram-пользователю |
| CRM-бот | Одна папка **«Авто под заказ»** → плоский список **«имя клиента · страна»** → детали заявки; без вложенных папок моделей/стран и без каталога фото |
| Общая запись | Одна изолированная база заявок; повтор одной отправки возвращает прежний номер; уведомление поставлено в outbox той же транзакцией; доставка отслеживается по каждому получателю |

Направления: Корея, Япония, Америка (США), Европа, Китай, Канада, ОАЭ, Грузия.
«Европа» — согласованное название направления закупки.

Локально проверены контракт, повторы/конкуренция, подписи/права, совместимые
черновики, состояния бота, плоский список CRM и ограниченное преобразование
HTML. Дополнительно пройден маршрут HTTP handoff → клиентский адаптер бота →
подтверждение → плоский список CRM → детали → outbox, с сохранением всех полей
и одной заявкой при повторе. Дополнительно проверены старые входы/выходы через настоящий диспетчер PTB,
доставка остальным при ошибке менеджера, отсутствие повторов подтверждённому
адресату и изоляция ошибки конфигурации нового раздела. Нативная библиотека PTB проверена с транспортом,
запрещающим сеть. В сквозном тесте отправка сообщений заменена локальными mocks.

Визуальная проверка сайта в браузере, мобильная проверка, целевой Python 3.10,
живой Telegram и сохранность фактического инвентаря после установки ещё не
проверены. Локальный preview был заблокирован средой; ограничение не обходили.
