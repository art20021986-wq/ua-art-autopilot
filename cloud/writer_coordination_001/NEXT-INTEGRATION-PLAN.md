## Оставшаяся реализация маршрута

1. Использовать уже проверенный общий final17 v2 и handoff v3; исторические final15, failed final17 v1 и failed handoff v2 сохранить. Повторять закрытые изолированные испытания только при изменении соответствующего кода или конкретном новом риске.
2. Подключить постоянный серверный журнал и проверенные валидаторы разрешения/завершения к `platform_control.Controller`. Текущие callbacks — интерфейс интеграции, а не готовое доказательство полномочий. Нужен один проверенный постоянный исполнитель; эфемерный Actions-runner не заменяет серверный журнал.
3. Подключить и испытать первоначальное завершение старых WSGI/cron/manual писателей. Передача исходников установщику внутри holder уже реализована и испытана; не создавать ещё один standalone installer. Прежний процесс, ожидающий flock, может продолжить после смерти holder: пауза расписания и свежая квитанция этого не исключают. В официальном API PythonAnywhere есть disable/enable/reload и управление конфигурацией задач, однако это не квитанция полного завершения старых процессов. Не выдавать Tasks/Consoles UI-инвентаризацию за доказательство WSGI drain. Не держать DB/publication-lock в другом процессе во время обычного publisher — это вызовет взаимное ожидание.
4. Добавить отдельное авторизованное чтение свежей server-fence квитанции, затем чистую проверку её контекста. Привязать доказательство к proposal, execution receipt и recovery_verify; повторить challenge перед main-CAS. Изменения runtime требуют новой версионированной canary, не перезаписи старой.
5. Получить разрешённое доказательство работы десяти источников и загруженного worker, измерить очередь/повторы. Пакет `source_acceptance.py` и точный план подготовлены; выполненная 11:00 UTC повторная попытка в прежней локальной среде снова завершилась отменой запроса разрешения до решения. HTTP-ответов 0; обход через другой сервер не выполнялся. Не повторять без разрешённого доступа. В текущем плане vPIC проверяет только общую API-схему, Carisyou — техническую идентификацию страницы; для полной приёмки нужны соответствующие подтверждённые контрольные случаи в следующей версии плана. Пользователю не требуется выбирать технические URL.
6. Сформировать окончательный план на актуальный main и его SHA. Только после реального закрытия предыдущих условий требуется предусмотренная маршрутом отдельная команда владельца. Запрашивать её для ещё неисполняемого плана нельзя.
