# Точная стыковка восстановления16 с удерживаемым окном

9 сентября2026. UA-ART-SPEC-AUTO-10-RESTORE-001. Это проект интерфейса, **не готовый исполнитель**. Production не изменён; final17v3 и `CodeHandoff v4` сохранены побайтно.

## Почему существующие функции нельзя просто вызвать

1. `spec_publication.reconcile_published` открывает `.ua_art_publish_transaction.lock` новым `open("a+b")` и выполняет `flock(LOCK_EX|LOCK_NB)`. При удерживаемом FenceLease этот независимый fd получает `PUBLICATION_LOCK_BUSY`. Функция не принимает внешний lock context; замена глобальных `open`/`fcntl` или отключение flock неприемлемы.
2. `publish_transaction_guard._exclusive_lock` имеет настоящий thread-reentrant путь (`RLock` и thread-local depth). Однако он не передаётся в reconciler. Искусственная установка depth также не доказывает владение блокировкой и обходит штатную recovery-проверку.
3. `publish_transaction_guard.Snapshot` охватывает primary, diagnostics, catalogs и варианты HTML. Его restore не ограничен ровно32 исходными страницами и не проверяет ожидаемый наш postimage перед каждой компенсацией. Более того, текущий `guard_write` запрещает восстановить повреждённую preimage без спецификации обычным publisher writer. Этот backup нельзя объявить готовым rollback для исходно повреждённых страниц.
4. Reconciler хранит rollback двух страниц одной карточки только в памяти. Он не представляет общую транзакцию32 файлов и условного изменения года в SQLite; после смерти процесса такой набор может остаться частично применённым.

Поэтому безопасная реализация требует отдельной узкой **DATA-транзакции** в том же holder. Она может повторно использовать проверенные файловые примитивы `_read`, `_exclusive`, `_sync` из handoff, но не должна подклассифицировать `CodeHandoff`, подменять его manifest или ослаблять допуск17 исходников. Непроверенный новый исполнитель в текущем этапе не добавлен.

## Входы будущей операции

Предлагаемый интерфейс: `Manual16DataHandoff(lease, payload_dir, bound_plan, verify_window=...).apply()`; отдельные `read_terminal()` и `rollback_only()` используют тот же план. Ни CLI-флаг авторизации, ни стандартный положительный verifier не предусматриваются.

| Вход | Точное ограничение |
| --- | --- |
| `lease` | Реальный текущий `server_fence.FenceLease`: тот же PID и поток, `held=true`, все шесть существующих inode, текущий persistent intent; fd заимствуются, не открываются повторно, не закрываются операцией |
| `payload_dir/private-plan.json` | Схема `UA-ART-MANUAL16-PREPARED-PAYLOAD-1`, SHA от canonical JSON без поля самого SHA; разрешение исполнения привязано именно к этому SHA |
| `payload_dir/candidate/<path>` | Ровно `video/UA-0001.html`…`video/UA-0016.html` и те же16 в `site`; проверка before/after SHA, размера, режима, отсутствия symlink/hardlink/подменённых родительских каталогов |
| CRM | Только уже существующая `crm.db`; все18 полных строк должны совпадать со снимком. Разрешена ровно одна условная ячейка `cars.year`, UA-0016, VIN…1028, `published=1`, `1999 → 2017`. ID и полный VIN берутся из утверждённого manifest, не выводятся из номера |
| Защищённые черновики | UA-0017/UA-0018: `published=0`, SHA обеих полных строк и прежнее наличие/отсутствие четырёх primary-файлов. Автопубликация запрещена |
| Спецификация | Read-only текущая canonical spec DB; semantic SHA тех же полей обеих таблиц, которые использовал `build_verified_specs.py`; свежий сетевой сбор в эту операцию не входит |
| `bound_plan` | SHA payload, source pins DATA executor/файловых примитивов, точная session main/run/nonce/epoch, SHA контрольного плана и независимого разрешения, scope32HTML+oneSQLcell; не выдаётся за HALT-removal plan |
| `verify_window` | Реальная независимая проверка текущих полномочий, паузы и полного prior-writer drain; новый challenge и свежий ответ перед backup, каждым изменением, commit, readback и compensation. При отказе записи прекращаются |

Для строгого сравнения всех18 строк подготовитель закрепил `crm_all_rows_sha256` и `crm_proposed_all_rows_sha256`: SHA canonical списка полных строк `SELECT * FROM cars ORDER BY auto_number`, с BLOB как `{ "bytes_hex": ... }`. Хэш только выбранных identity-полей не защищает остальные ручные поля. Эти поля и `spec_semantic_fields` фактически присутствуют в свежем частном payload `manual16-payload-r9-v3`, SHA плана `301e45050ce7a163825e0429d36929d81f4d4fe723c3342af166baf3fc311597`; SHA пересчитан независимо. Само наличие payload не означает наличие DATA executor или разрешения исполнения.

## Обязательный порядок внутри того же holder

1. Проверить реальную window authority, закреплённые исходники, исходные32 SHA, полный CRM fingerprint, неизменность spec и обеих draft-карточек. Проверить отсутствие незавершённой старой DATA-транзакции. Новый план не присваивается старому journal.
2. Проверить свежую квоту аккаунта70/80/90 по существующим правилам и абсолютные свободные bytes. Эксклюзивно создать `lease.directory/manual16-data` с планом, append-only journal и backup manifest. Сохранить все32 preimage вместе с mode/mtime; получить согласованный SQLite backup до первой записи. Отдельно закрепить before/after полной строки UA-0016.
3. Открыть **существующую** CRM через `mode=rw`; получить SQLite `BEGIN IMMEDIATE`, не меняя режим journal и не импортируя CRM. Запретить trigger/SQL-записи вне `cars.year` и проверить схему. Перед SQL проверить полный ожидаемый набор18 строк; SQL выполняется параметрами и обязан затронуть ровно1 строку. Изменение года пока остаётся незакоммиченным.
4. Подготовленные HTML не генерировать заново на живых данных и не вызывать обычный publisher. Перед каждой replace записать intent с expected before/after, fsync journal; заново проверить window и целевую preimage. Использовать эксклюзивную временную запись и атомарную замену в том же каталоге, затем fsync каталога и readback. При повторе принять только текущий before или ровно наш after, никогда чужую версию.
5. Проверить все32 after, оба draft-файла/строки и spec. Проверить все18 CRM-строк с единственным ожидаемым изменением года. Зафиксировать durable `BEFORE_SQL_COMMIT`; commit года выполняется последним. После commit прочитать CRM заново, затем записать терминальный `DATA_LOCAL_COMMITTED`. Это ещё не публичная приёмка и не разрешение включить CRM/снять HALT.
6. При исключении до commit SQLite откатывает незакоммиченный год. Компенсация HTML разрешена только из сохранённого backup и только если целевые bytes равны нашему before или after; обнаружение чужой версии прекращает весь rollback до перезаписи этой версии. При необходимости после commit компенсировать только нашу ячейку года при полном совпадении ожидаемой after-строки; чужие ручные правки не затирать.
7. После смерти процесса recovery читает именно durable journal, backup manifest и фактический before/after CRM. Файла `COMMITTED` без свежего readback недостаточно. Незавершённая операция сохраняет intent и паузу; новая независимая проверка drain нужна и для rollback-only. Исполнитель сам не включает задачи и не снимает HALT.

Проверка публичных URL всех16 карточек и фактической загрузки исправленного CRM выполняется отдельным допущенным terminal-controller. Только затем можно сообщить владельцу готовность кнопки UA-0017. После её ручного нажатия принимается реальная публикация/URL, затем допускается UA-0018.

## Минимальные испытания до допуска

Нужен один настоящий isolated32-page+18-row цикл на том же FenceLease, без повторного publication flock. Проверки: отказ отсутствующей authority до первой записи; частичная запись страницы → точная компенсация; потеря процесса до/после SQL commit → recovery из journal; чужая HTML/CRM правка → отказ перезаписи; неизменность двух черновиков и spec; повторное чтение терминального состояния без новой записи. Проверки старого code installer не повторяются для счётчика.

Этот объём является новой транзакционной реализацией, а не коротким подключением имеющегося метода. Он не завершён и не объявлен серверным PASS. Внешний WSGI drain остаётся отдельной реальной предпосылкой рабочих записей; дизайн этого интерфейса не предоставляет её.
