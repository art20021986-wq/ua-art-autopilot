# ORDER-GUARD — короткий сбой базы заказов не присылать как «Ошибка в боте»

Задача: `tasks/BOT-ORDER-STORAGE-001.md`. Проба: `cloud/order_storage_check_001/evidence.json`
(13.11 10:19–16:24 UTC: 7 сбоев за 6 ч, все в claim_notification, самый длинный 46 с).

Модули:
- `ua_order_outbox_guard.py` → `ua_order/outbox_guard.py` (новый) — считает сбои подряд; «да» ровно один раз,
  когда отказ длится 5 минут; после удачного шага сбрасывается.
- `ua_order_bindings.py` → `ua_order/bindings.py` (замена) — задание очереди уведомлений (каждые 5 с):
  StorageUnavailable пишется в журнал и повторяется следующим шагом; владельцу (существующий обработчик
  «⚠️ Ошибка в боте») — только при отказе 5+ минут. Остальные ошибки — как раньше.
- `ua_order/mysql_repository.py` — точечная вставка в живой файл (`candidate_builder.patch_repository`): код ошибки
  MySQL в журнал бота перед тем, как он скрывается. Нужен, чтобы при следующем сбое была видна причина.
- `deployment_*`, `make_release.py` — установка по образцу `cloud/crm_new_car_vin_002`.

Документация: python-telegram-bot — исключения из заданий JobQueue уходят в обработчики ошибок приложения;
ожидаемые временные сбои обрабатываются в самом задании. Повтор — сам интервал задания (5 с), очередь уведомлений
в MySQL не теряет заявку (не взятое уведомление берётся следующим шагом).

Тесты: `test_outbox_guard.py` (сторож, сборка на точных серверных версиях, настоящее задание bindings.py с падающей
базой), `test_deployment.py` (бэкап, установка, откат, пауза бота).
