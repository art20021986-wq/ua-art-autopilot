Система: Telegram CRM-бот + клиент-бот UA ART

Главный критерий: CRM быстро, безошибочно и непрерывно работает во время эксплуатации и ремонта.

## 1. Цель

Создать устойчивый операционный контур, в котором:

1. CRM-бот и клиент-бот доступны постоянно и не зависят от изменений публичного сайта.
2. Любое обычное действие CRM завершается не позднее 5 секунд после получения события ботом.
3. Фото и видео принимаются без потерь, дублей, неверных счётчиков и блокировки интерфейса.
4. Голос, текст, OCR фото и речь/кадры видео заполняют только допустимые поля текущей открытой карточки.
5. Уже заполненные поля не перезаписываются без явной команды исправления.
6. Новая карточка не создаётся неявно; текущая карточка не теряется.
7. Серверный онлайн-контроль без LLM-токенов обнаруживает задержки и известные сбои и выполняет безопасное автолечение.
8. Владелец продолжает работать в CRM во время диагностики, установки и восстановления; входящие события не теряются.

## 2. Область задания и порядок дополнений

## 3. Граница измерения пяти секунд

Отсчёт серверной задержки начинается в момент, когда Telegram передал update приложению CRM. Время загрузки файла с телефона до Telegram и внешняя мобильная сеть измеряются отдельно и не могут контролироваться сервером CRM.

Для большого фото/видео действие считается принятым, когда в пределах 5 секунд бот:

- записал уникальный идентификатор события в надёжную очередь;
- закрепил правильную карточку и тип вложения;
- показал владельцу «принято / в очереди / сохранено»;
- гарантировал последующую обработку без повторной отправки.

Фоновая обработка не имеет права блокировать кнопки, голос, текст или приём следующих файлов.

## 4. Жёсткие SLO/SLA

| Действие | Цель p95 | Жёсткий предел | Реакция при нарушении |
|---|---:|---:|---|
| ACK на кнопку | ≤ 0,5 с | ≤ 1 с | безопасный ACK продолжается даже при ошибке Telegram |
| Открытие экрана/карточки | ≤ 2 с | ≤ 5 с | один безопасный retry, затем fallback-экран |
| Запись одного текстового поля | ≤ 2 с | ≤ 5 с | очередь единственного писателя, проверка результата |
| Приём update с фото/видео в очередь | ≤ 1 с | ≤ 5 с | durable enqueue, circuit breaker тяжёлой обработки |
| Обновление прогресса медиапакета | ≤ 2 с | ≤ 5 с | одно редактируемое статус-сообщение |
| Голос: ACK | ≤ 0,5 с | ≤ 1 с | немедленный статус без ожидания STT |
| Голос: финальный результат | ≤ 4 с | ≤ 5 с | отмена медленного STT, безопасный ответ без записи, один фоновый сетевой retry |
| Проверка SQLite | ≤ 1 с | ≤ 3 с | ограниченный retry/backoff, затем режим сохранения очереди |
| Обнаружение зависшего процесса | ≤ 3 с | ≤ 5 с | перезапуск компонента, не всей системы |

Допуск: **0 необъяснённых действий свыше 5 секунд** в приёмочных испытаниях. Любое превышение является P0-инцидентом.

## 6. Фундаментальные правила данных

### 6.1 Нормальный режим заполнения

Перед каждым текстом, голосом, OCR или видео бот заново читает карточку из БД и вычисляет список незаполненных полей.

- Разрешено записывать только поле из живой CRM-схемы и списка недостающих.
- Значение, уже равное сохранённому, является idempotent no-op.
- Другое значение для заполненного поля не записывается и не ставится поверх него.
- Неизвестное, двусмысленное или низкоуверенное значение не записывается.
- Один input привязан к одному зафиксированному `card_id`.
- Новая карточка не создаётся автоматически.

### 6.2 Явный режим исправления

Перезапись разрешается только:

- через кнопку редактирования конкретного поля; или
- командой `измени/исправь/замени <поле> <значение>` и её RU/UA/EN эквивалентом.

Меняется только названное поле. Перед записью бот показывает старое и новое значение, после записи повторно читает БД и предлагает однократную отмену.

### 6.3 Атомарность и защита от гонок

- Нормальная запись: compare-and-set `UPDATE ... WHERE поле пустое`.
- Исправление: compare-and-set по ожидаемому старому значению/версии карточки.
- После commit выполняется read-back; пользователю показывается только фактически сохранённое значение.
- Частичный commit нескольких полей запрещён: либо весь допустимый набор, либо rollback.
- История содержит источник, время, card_id, поля и результат без сохранения секретов.

## 7. Голос, текст, фото и видео

### 7.1 Единый конвейер

Все источники проходят один порядок:

1. зафиксировать текущую открытую карточку;
2. прочитать свежие данные и недостающие поля;
3. получить текст источника один раз;
4. нормализовать RU/UA/EN, порядок слов, единицы и синонимы;
5. сопоставить только с живой CRM-схемой;
6. применить приоритет источника и confidence;
7. атомарно записать допустимые недостающие поля;
8. перечитать БД;
9. показать `добавлено / уже было / не распознано / время`.

### 7.2 Голос

- Одна расшифровка на сообщение; второй вызов допустим только один раз после доказанного сетевого сбоя и выполняется вне блокирующего 5-секундного окна.
- Для короткой речи владельца восстановить last-known-good `language=ru`; RU/UA/EN и автомобильные английские термины сохраняются подсказкой. Автоопределение разрешено как один ограниченный fallback, только если первая расшифровка пуста или явно не соответствует языку, без двойной записи.
- STT получает дедлайн не более 3,2 с, парсер ≤ 0,3 с, commit/read-back ≤ 0,5 с.
- При превышении дедлайна карточка не меняется, пользователь получает результат не позднее 5 секунд, событие остаётся в безопасной очереди.
- Транскрипция и извлечённые поля логируются раздельно в обезличенном виде/хеше для диагностики качества.
- Команды с изменённым порядком слов обязаны распознаваться: `LPI топливо`, `engine two liters`, `білий колір`, `цвет машины белый`.

### 7.3 Канонические значения

Обязательный единый словарь:

- LPI ≠ LPG ≠ gasoline; слово `gas` без контекста не записывается автоматически.
- `2.0`, `2 литра`, `2000`, `two liters` → `engine_cc=2000`.
- Цвета RU/UA/EN приводятся к одному канону.
- Пробег, цена, год, привод, КПП имеют диапазоны и единицы.
- VIN проверяется отдельно и никогда не создаёт новую карточку без явной команды.

Критический golden-тест: `тип топлива LPI, объем двигателя 2000, цвет белый`.

### 7.4 Фото и видео как источник анкеты

- Любое фото или видео, направленное в контексте открытой карточки, сначала надёжно принимается и сохраняется без ожидания OCR/ИИ.
- Подпись, видимый текст, маркировка, документы, ограниченное число информативных кадров и звуковая дорожка автоматически проверяются на значения полей карточки.
- Извлекаются только значения из живого whitelist CRM и только для недостающих полей; посторонний текст, люди, фон, сайт и декоративная информация отбрасываются.
- Медиаанализ выполняется после durable enqueue и не имеет права замедлять приём файла, кнопки и следующие сообщения свыше 5 секунд.
- Сильное однозначное значение записывается через тот же валидатор/CAS, что текст и голос. Среднее предлагается для подтверждения. Слабое или выведенное только по внешнему виду не записывается.
- Заполненное значение не перезаписывается результатом фото/видео. Один файл и повторный Telegram update не создают повторных записей.
- По внешнему виду запрещено угадывать год, двигатель, пробег или техническое состояние; эти поля принимаются из читаемого текста/документа/речи либо из явного сообщения владельца.

### 7.5 Приоритет и confidence

1. Явное поле владельца в режиме исправления.
2. Выбранное кнопкой поле.
3. Маркированный документ/OCR `поле: значение`.
4. Сильный словарь + единица измерения.
5. Структурированный текст.
6. Слабая эвристика — только предложение, без записи.

Высокая уверенность записывается автоматически; средняя требует одного подтверждения; низкая отклоняется.

## 8. Медиа: скорость, порядок и точный счётчик

- Уникальность события: `bot_id + chat_id + message_id + file_unique_id + card_id + target`.
- `file_id` используется для Telegram, `file_unique_id` — для дедупликации; повтор одного update всегда no-op.
- Durable spool записывается атомарно до ответа владельцу.
- Один drain владеет глобальным lock; остальные работники не дублируют commit.
- Сохраняется исходный порядок Telegram updates.
- Счётчик всегда разделён: `Принято сейчас`, `Сохранено сейчас`, `Всего в карточке`, `Очередь`, `Отклонено как дубль`.
- 17 отправленных новых уникальных фото не могут отображаться как 18 или 20 новых; общий старый остаток показывается отдельным числом.
- Лимит 100 проверяется без off-by-one; 100/100 принимается, 101-е отклоняется с ясным сообщением.
- Прогресс объединяется в одно редактируемое сообщение не чаще одного раза в секунду; сообщения на каждое фото не засоряют чат.
- После завершения пакета доступны `Открыть текущую карточку` и `Создать новый автомобиль`; второй пункт создаёт карточку только после явного нажатия.
- Ошибка сайта, OCR, превью или дизайна не блокирует приём медиа.

## 9. Кнопки «Доставка и этапы» и «Комплексная диагностика»

Для каждого callback вводится общий безопасный wrapper:

- записать `event_id`, callback prefix, card_id и время старта;
- выполнить `q.answer()` с коротким тайм-аутом; просроченный ACK не отменяет открытие экрана;
- заново прочитать карточку;
- сформировать лёгкий текстовый экран без тяжёлых операций сайта/медиа;
- отправить или отредактировать сообщение;
- зафиксировать время и результат;
- при первой сетевой ошибке выполнить один безопасный retry;
- при исключении показать fallback-кнопку возврата и не оставлять бесконечный spinner.

На старте приложение выполняет route self-test: callback кнопки должен иметь ровно один обработчик. Дубли, отсутствующий handler и перекрывающий pattern блокируют релиз.

Приёмка обеих кнопок выполняется реальным Telegram-нажатием на свежей карточке и на старом сообщении, а не только статическим поиском строки в коде.

## 10. Развязка CRM и сайта

- CRM commit является первичным и не вызывает синхронную генерацию сайта.
- Обновление сайта получает отдельное событие outbox и выполняется фоном.
- Ошибка или изменение HTML/CSS/генератора сайта не влияет на кнопки, карточки, голос, фото и SQLite CRM.
- В CRM остаются компактные числа и операционные действия; тяжёлый веб-дизайн в сообщения не загружается.
- Публичный сайт и существующие карточки не изменяются этим заданием без отдельной необходимости и проверки scope.

## 11. Клиент-бот

- Проверить `/start`, главное меню, `Открыть каталог`, подборы стран, условия и аналитику.
- Каталог открывается прямой Telegram WebApp/URL-кнопкой и имеет резервную обычную ссылку.
- Ошибка сайта возвращает понятный ответ и не останавливает бот.
- Клиент-бот имеет отдельный токен, heartbeat, latency и перезапуск; сбой CRM не останавливает клиент-бот и наоборот.
- Тестировать не только `getMe`, но и реальный пользовательский маршрут до каталога.

## 12. Постоянный CRM Online Guard без LLM-токенов

Guard работает внутри единого Always-On supervisor и не требует второго Telegram polling-процесса.

### 12.1 Частота и данные

- внутренний heartbeat каждого бота: 1 с;
- проверка event-loop lag: 1 с;
- очередь и возраст старейшего события: 1 с;
- SQLite quick probe: 5 с;
- Telegram API и диск: 30 с;
- сводка здоровья: атомарный JSON/sidecar SQLite;
- значения токенов, голос и персональные данные в метрики не попадают.

### 12.2 Метрики

- latency p50/p95/p99/max по каждому действию;
- callback ACK и screen latency;
- STT download/transcribe/parse/commit отдельно;
- число найденных, записанных, пропущенных и исправленных полей;
- попытки неявной перезаписи;
- undo/correction rate;
- медиа accepted/saved/duplicate/queue age;
- `database locked`, retry, commit duration;
- Telegram timeout/rate-limit;
- uptime и рестарты каждого компонента;
- обращения к внешнему STT, длительность аудио и стоимость; LLM-токены guard = 0.

### 12.3 P0-сигналы

- любое действие >5 с;
- callback без финального ответа;
- bot heartbeat отсутствует >3 с;
- очередь не уменьшается или oldest age >5 с;
- `database is locked` после ограниченного retry;
- потеря/дубль медиа;
- неявная перезапись поля;
- неожиданная новая карточка;
- рост исправлений/undo или пустых результатов STT;
- неверные/одинаковые токены ботов.

### 12.4 Безопасное автолечение

Разрешены только заранее проверенные действия:

1. отменить зависшую операцию и сохранить её в durable queue;
2. открыть circuit breaker тяжёлого OCR/STT/сайта;
3. переподключить Telegram/DB с bounded backoff;
4. перезапустить только неисправный компонент;
5. восстановить очередь;
6. откатить последний релиз к last-known-good при совпадении контрольных сумм;
7. уведомить владельца через второй работающий бот.

Неизвестная ошибка не разрешает guard самостоятельно генерировать или менять код. Он сохраняет работу ядра, фиксирует доказательства и переводит дефект в P0-разбор. Максимум 3 рестарта за 15 минут; далее безопасный режим без restart-loop.

Каждая устранённая причина получает постоянный regression test, чтобы тот же класс ошибки не повторился.

## 13. Непрерывная работа во время ремонта

- До установки: полный backup и снимок SHA/DB/media counts.
- Изменения сначала проходят shadow-компиляцию и тест на копии БД.
- Файлы переключаются атомарным `os.replace`, без частичного состояния.
- На коротком перезапуске Telegram updates остаются в очереди; durable spool принимает медиа до/после handoff.
- Контролируемый handoff ≤3 с; общий предел ответа 5 с.
- Если новая версия не даёт heartbeat/route PASS, автоматический rollback выполняется до приёма новых записей.
- Владелец может продолжать нажимать кнопки, отправлять текст, голос и медиа; повторная отправка после релиза не требуется.

## 19. P0-дополнение VOICE-RESTORE-01: восстановление смыслового ИИ микрофона

Основание: реальный тест владельца 29.08.2026, два голосовых сообщения по 3 секунды. STT вернул непустой текст, однако бот дважды ответил: `Не распознал поле CRM`. Карточка осталась без пробега, описания, цены продажи и статуса.

Повторный аудит установил регрессию:

1. В раннем рабочем контуре после расшифровки использовались существующие `ai.parse_message → ai.validate → ai.to_card_data` и смысловой `auto_catch`.
2. Текущий быстрый голосовой обработчик перехватывает сообщение раньше `auto_catch` и пропускает его только через локальные regex/fast-парсеры.
3. Специальный `_v167_voice_explicit_fields` разбирает преимущественно топливо, объём и цвет; свободные фразы про пробег, описание, цену продажи и статус могут дать пустой результат.
4. В v1.3 принудительный `language=ru` был заменён автоопределением, что создало дополнительный риск ошибки на короткой русской записи.

### 19.1 Обязательная новая логика

1. Сначала выполнить одну качественную STT-расшифровку с last-known-good языковой настройкой и автомобильной подсказкой.
2. Прочитать свежую текущую карточку и сформировать whitelist только реально недостающих полей с их типами и допустимыми значениями.
3. Запустить нулевой по LLM-токенам детерминированный parser fast path.
4. Если текст есть, но fast path не дал уверенного допустимого результата, немедленно вызвать существующий смысловой AI-parser один раз с минимальным контекстом: транскрипция + whitelist недостающих полей. Фото, вся карточка, сайт и заполненные значения в запрос не передаются.
5. AI обязан вернуть строгий JSON только по whitelist. Результат повторно проходит `ai.validate`, CRM-схему, диапазоны, нормализацию и CAS.
6. Заполненное поле остаётся неизменным. Для замены требуется явное `измени/исправь/замени` и название поля; меняется только оно.
7. Голос всегда относится к открытой карточке. Создание новой карточки из голосового сообщения запрещено.
8. Если значение уже занесено, бот отвечает `уже заполнено` вместо ложного `не распознал`.
9. Если значение действительно не определено, ответ показывает краткую транскрипцию `Я услышал: …` и перечень ещё недостающих полей, чтобы диагностировать STT без доступа к аудиофайлу и без повторной отправки вслепую.
10. Аудио и полный текст не сохраняются в постоянных логах; фиксируются только длительность, выбранный путь `fast/semantic`, количество полей, результат, latency и стоимость. Online Guard остаётся с 0 LLM-токенов.

### 19.2 Скорость и стоимость

- ACK микрофона ≤1 с; финальный результат ≤5 с.
- Загрузка аудио ≤1,1 с; STT получает основной бюджет; semantic fallback имеет жёсткий короткий timeout и circuit breaker.
- Одна STT-операция на сообщение. Второй STT разрешён только после пустой/языково ошибочной расшифровки и не имеет права выполнить повторный commit.
- Fast path использует 0 LLM-токенов. Semantic fallback использует один минимальный структурированный запрос только при необходимости; токены и стоимость учитываются пооперационно.

## 20. P0-дополнение INPUT-DB-ROUTES-02: все источники, пробег, контейнер и SQLite

Основание: реальные проверки владельца 29.08.2026 на существующих карточках.

### 20.1 Зафиксированные симптомы и доказательства

1. В открытом редакторе поля `Пробег` голосовое число не принято: бот ответил `Не разобрал число. Пришлите цифрами.`
2. После этого чистое текстовое значение `163400` также не получило подтверждения и не появилось в карточке.
3. Меню контейнера открылось, но нажатие `Ввести номер контейнера` сначала не дало результата; после повторного входа приглашение появилось, а отправленное `ONEYSELGF1046602` не получило подтверждения сохранения.
4. Боевой traceback при смене этапа зафиксировал точный путь: `stage_set → set_field → db.update_card_field → connect.__exit__/commit → sqlite3.OperationalError: database is locked`.
5. Одна причина блокирует разные операции записи: этап, контейнер, пробег и другие поля. Локальное исправление одной кнопки без ремонта общего writer-контракта запрещено.

### 20.2 Единый контракт входных данных

- Все поля карточки должны приниматься из любого доступного источника: текст, чистое число, голос, аудио, подпись к фото/видео, OCR изображения, речь/кадры видео и выбранное кнопкой поле.
- Источник преобразуется в один объект `FieldCandidate(field, value, source, confidence, card_id, event_id)` и проходит единые schema/normalization/range/CAS/read-back правила.
- Если владелец уже выбрал конкретное поле кнопкой, вход `163400` трактуется как значение этого поля; повторно произносить/писать слово `пробег` не требуется.
- Числа поддерживаются цифрами и словами, с пробелами, единицами и RU/UA/EN формами: `163400`, `163 400`, `163400 км`, `сто шестьдесят три тысячи четыреста` → `mileage_km=163400`.
- Лишняя информация игнорируется. Нужная карточке информация не отбрасывается из-за порядка слов, языка или типа источника.
- Заполненное поле не затирается без явного режима исправления; один event применяется не более одного раза.

### 20.3 Общий неблокирующий writer SQLite

- Все скалярные записи (`set_field`, этап, контейнер, дата, пробег, цена и остальные поля) обязаны идти через один writer-контракт.
- Операция делает короткую попытку commit с общим пределом менее 2 секунд. При `locked/busy/queue timeout` она атомарно помещается в durable FIFO field queue и немедленно получает ответ `Принято, сохраняю` в пределах 5 секунд.
- Worker выполняет последовательный commit, проверяет ожидаемое старое значение, делает read-back и отправляет финальное подтверждение. Повтор одного event — idempotent no-op.
- Исключение `database is locked` никогда не отправляется владельцу как traceback и не останавливает обработчик Telegram.
- Долгоживущие читатели не удерживают write-lock; любой lock имеет владельца, возраст и bounded timeout. Зависший lock обнаруживается guard и безопасно освобождается/перезапускается без потери очереди.
- Аудит записи не может отменить уже успешный commit: при блокировке журнала audit отдельно ставится в очередь.

### 20.4 Контейнер и дата отправления

- `Номер и дата контейнера`, `Ввести номер контейнера`, `Ввести дату отправления` и `Пропустить` имеют ровно по одному зарегистрированному callback-маршруту.
- Маршрут обязан работать на всех существующих и будущих карточках; логика не зависит от номера карточки, наличия страницы сайта или даты создания.
- Номер контейнера нормализуется в верхний регистр, проверяется по допустимому формату 4–20 латинских букв/цифр, сохраняется в `sea_container` и подтверждается read-back.
- Значение `ONEYSELGF1046602` является обязательным golden-тестом.
- Дата проходит строгую нормализацию, сохраняется один раз и не меняет этап без отдельного явного действия.
- Просроченный Telegram ACK не отменяет сохранение; пользователь всегда получает итог или безопасное сообщение очереди ≤5 секунд.

### 20.5 Жёсткая приёмка дополнения

1. Поле `Пробег`: текст `163400`, текст с единицей, число словами и голос — 4/4 корректных read-back; время каждого ≤5 секунд.
