# Ручное завершение инцидента 36268504600

Команда владельца: **«Убери блоки и установи»**, 27.09.2026.

`reconcile_delivery.py` — отдельный маршрут ровно для прежней установки
`DELIVERY-STATUS-INSTALL-20260927`. По образцу ранее описанного incident-specific
forward reconciliation в `docs/incidents/TASK088-STAGE2-INSTALL-34734575941.md`
он подтверждает фактически выполненную установку исходников без повторного
отката. Маршрут TASK120 не используется, общие автоматические проверки не меняются.

Регистрация в `state/manual_recovery_routes/` привязана к точному SHA скрипта,
текущему runtime manifest и команде владельца. Сам скрипт **ничего не пишет**,
не обращается к сети, не получает токенов и не перезапускает процессы.

Перед применением требуются наблюдения не старше 120 секунд:

- точные исходники всех 11 файлов прежней установки и защищённых Python-модулей;
- целые manifest, база и все before/after файлы резервной копии;
- подлинные результаты backup/install/verify для исходного run и plan, законченный
  журнал установки и отсутствие результата rollback;
- только штатные процессы бота и монитора, работающий бот;
- полная очередь GitHub для пяти активных статусов без выполняющихся заданий;
- доступность двух канонических публичных страниц.

Сведения о последующих исправлениях остаются отдельными: `full_crm_acceptance`
и `publication_repair_installed` должны быть **false**. Публикация UA-0021 и
синхронизация новых правок этим переходом не объявляются исправленными.

Предложение содержит ровно девять путей: точные архивы прежних HALT/transaction/
claim, фактическую квитанцию прежней установки, доказательства и решение,
завершённые transaction/claim и удаление только активной копии HALT.
Исходные request, approval, consumed ledger и nonce сохраняются без изменений.
История ошибки в claim сохраняется. Откат не называется выполненным.

Оператор должен применить эти байты **одним Git commit с одним точным ожидаемым
родителем**, после чего одним non-force ref update. Если main изменился,
переносить старое предложение нельзя: нужны свежие наблюдения и новый план.
До первого изменения main сравнить SHA его исходных HALT/transaction/claim/request
с `original_state_sha256` предложения. После записи — ответное чтение всех
девяти путей, проверка сохранения nonce/ledger/runtime и неизменённые `verify-mode`
и `assert-clear`. Успех локальной модели не считать выполненной записью.

Проверки: 7 тестов, включая 20 отрицательных вариантов доказательств;
положительная модель выполняет оба действующих валидатора после перехода.
Она не доказывает результат на рабочем main. Ни регистрация, ни этот переход
не заменяют свежие preflight, backup, Gate B и Actions для четырёхфайловой
установки `crm_oneclick_publish_001`.
