# План установки GitHub Actions (после одобрения владельца) — TASK_010

## Разделение архитектуры на два независимых потока

### Поток 1 — Автоматическая передача в карантин (транспорт), уже частично существует
Workflow: `PythonAnywhere Inbox Sync` (существующий, требует исправления секрета).

- Триггер: push в ветку задачи / merge в main, затрагивающий `cloud/**`.
- Действие: копирование содержимого `cloud/**` в `/home/Carix/autopilot_inbox/cloud/` через PythonAnywhere Files API.
- Это ТОЛЬКО транспорт. Никакого выполнения, никакого импорта, никакой публикации.
- Обязательный секрет: `PYTHONANYWHERE_API_TOKEN` (сейчас отсутствует/пуст — по этой причине последняя синхронизация упала).
- Обязательная переменная: `PYTHONANYWHERE_USERNAME` (например `Carix`), не секрет, но должна быть задана как Actions variable.
- Выход: машинная квитанция синхронизации (лог + список скопированных файлов + их SHA-256) сохраняется как артефакт workflow.

### Поток 2 — Генерация манифеста релиза (новый workflow, требует отдельного согласования до установки)
Workflow (предлагаемое имя): `Release Manifest Builder`.

- Триггер: успешное завершение Claude Autopilot Actions для задачи, коммитящей файлы в `cloud/`.
- Шаги:
  1. Собрать список изменённых `cloud/**` файлов из коммита.
  2. Посчитать SHA-256 каждого файла.
  3. Сформировать канонический манифест по `release_manifest_spec.md`.
  4. Закоммитить манифест в `cloud/approval_gate/releases/<task_id>_<short_sha>.json`.
  5. НЕ выполнять, НЕ помечать gate_a/gate_b — эти поля остаются `null` до владельца.
- Требуемые секреты: НЕТ новых секретов (использует только `GITHUB_TOKEN` для коммита).

### Поток 3 — Исполнение по Gate A (после явного одобрения владельцем, НЕ разворачивается в этой задаче)
Workflow (предлагаемое имя): `Gate A Safe Execution`.

- Триггер: ТОЛЬКО ручной `workflow_dispatch` с обязательным вводом `manifest_sha256`, инициируемый администратором после того как владелец прислал точную фразу `APPROVE_RUN ...` через доверенный канал (в будущем — MCP-коннектор, коротко описанный в `claude_owner_approval_mcp.py`).
- Шаги:
  1. Проверить, что `manifest_sha256` совпадает с последним сгенерированным манифестом для задачи.
  2. Проверить наличие валидной записи `gate_a` (создаётся отдельным, защищённым процессом одобрения, НЕ этим workflow).
  3. Вызвать `pythonanywhere_approval_gate.py::run_gate_a` НА СТОРОНЕ PythonAnywhere (через задачу/консоль, управляемую владельцем), не напрямую из GitHub Actions с боевыми учётными данными.
  4. Сохранить машинную квитанцию как артефакт.
- Обязательные секреты (на будущее, НЕ создавать сейчас): `PYTHONANYWHERE_API_TOKEN` (уже требуется для потока 1), возможно отдельный `PA_GATE_EXECUTION_TOKEN` с ограниченными правами.

### Поток 4 — Gate B (критическая публикация) — НЕ разворачивается
- Требует отдельного `workflow_dispatch` с ДВУМЯ независимыми подтверждениями (owner phrase + admin review), отдельного набора секретов с правом записи в продакшн-пути, отдельного визуального ревью перед стартом.
- Не проектируется подробно в этой задаче за рамками уже описанной модели Gate B в спецификации манифеста и в шлюзе.

## Точный безопасный порядок операций

1. Claude пишет файлы → коммит в `cloud/`.
2. Поток 1 копирует байты в карантин (если секрет настроен) — это уже безопасно и не требует одобрения.
3. Поток 2 генерирует манифест и коммитит его в `cloud/approval_gate/releases/`.
4. Владелец читает статус, видит хэши/риск/режим.
5. Владелец при необходимости запускает Gate A вручную точной фразой.
6. Только после этого — Поток 3 (при будущем разворачивании) проверяет всё заново на стороне шлюза и выполняет только заявленное безопасное действие.
7. Если требуется прод — отдельно, вручную, Gate B, только после визуальной проверки.

## Требуемые секреты/переменные (без значений)

- `PYTHONANYWHERE_API_TOKEN` (Secret) — необходим для Потока 1; сейчас отсутствует, это подтверждённая причина падения синхронизации.
- `PYTHONANYWHERE_USERNAME` (Variable) — необходим для Потока 1.
- Секреты для Потоков 3 и 4 НЕ создаются в рамках TASK_010.

## Поведение при сбое

- Любая ошибка проверки хэша/allowlist/происхождения → workflow завершается с ошибкой, никакая последующая стадия не запускается.
- Отсутствие секрета `PYTHONANYWHERE_API_TOKEN` → Поток 1 явно падает с понятной ошибкой, а не тихо пропускает шаг.
- Любая расхождение файла с манифестом после генерации → манифест считается недействительным, требуется пересборка (Поток 2 заново), старое одобрение аннулируется автоматически по конструкции (SHA изменится).
