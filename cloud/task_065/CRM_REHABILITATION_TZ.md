# CRM-REHABILITATION-003 v1.0

Статус: утверждено владельцем фактическими командами «исправить» и «сделать».
Дата: 28.08.2026.
Приоритет: критический.
Системы: BOT CRM, BOT client, SQLite `crm.db`, Telegram media, voice/text/OCR.

## 1. Конечная цель

Оба бота постоянно запущены и быстро отвечают. CRM сохраняет каждую принятую
фотографию ровно один раз, показывает честные счётчики, не блокирует SQLite,
а голос, текст и OCR записывают распознанные поля именно в открытую карточку.
Изменения сайта не должны ломать этот контур.

## 2. Подтверждённые причины аварии

1. Несколько параллельных обработчиков сливали одну фотоочередь и могли работать
   со старым снимком карточки.
2. SQLite получала конкурирующие записи и возвращала `database is locked`.
3. Сообщение прогресса смешивало фотографии текущей отправки и общий итог
   карточки.
4. Голос был распознан, но заполненные поля не обновлялись без слова «измени».
5. Старый детерминированный парсер не распознавал `LPI`, число `2000` без единицы
   измерения и русский цвет в естественной голосовой фразе.
6. В `UA-0011` фактически пусты `fuel`, `engine_cc`, `color`; фотографии:
   22 уникальных Telegram `file_id`, точных дублей нет, очередь равна нулю.

## 3. Обязательные функциональные требования

### 3.1. SQLite

- Все записи выполняются через централизованный соединительный слой task_064.
- `busy_timeout`, повтор commit и межпроцессная сериализация сохраняются.
- Ошибка `database is locked` не должна выходить пользователю traceback-ом.
- `PRAGMA quick_check` после установки обязан вернуть `ok`.
- Установка не изменяет карточки, кроме трёх явно заданных владельцем полей
  `UA-0011`: `fuel=LPI`, `engine_cc=2000`, `color=белый`.

### 3.2. Фотографии

- Приём фото отделён от медленной обработки и не вызывает LLM.
- Перед подтверждением `file_id` атомарно попадает в долговечную JSONL-очередь.
- Ровно один процесс владеет глобальной блокировкой слива очереди.
- Повторный `file_id` идемпотентен и не увеличивает счётчик.
- Порядок фотографий сохраняется.
- Лимит карточки: 100; переполнение не повреждает уже принятые элементы.
- После серии бот отправляет одно компактное сообщение и одну кнопку
  «Открыть карточку», без тяжёлого повторного меню после каждого фото.
- Формат прогресса:
  `Добавлено сейчас: X · всего: Y/100 · очередь: Z`.
- `X` — уникальные фото текущего сеанса; `Y` — уникальный итог карточки;
  `Z` — ещё не записанная очередь.
- Переход «Открыть карточку» завершает режим загрузки и возвращает к рабочей
  карточке для следующей операции.

### 3.3. Голос, текст и OCR

- Голос применяется только к явно открытой карточке.
- Голосовое сообщение никогда автоматически не создаёт новую карточку.
- Названное поле считается явной командой на изменение; слово «измени» не нужно.
- Детерминированно поддерживаются варианты `LPI/ЛПИ`, `LPG/ЛПГ`, объём в
  кубических сантиметрах или литрах, русские/украинские/английские цвета.
- Контрольный пример обязан дать:
  `тип топлива LPI, объём двигателя 2000, цвет белый` →
  `{fuel: LPI, engine_cc: 2000, color: белый}`.
- Записываются только поля, существующие в живой CRM-схеме.
- Существующий OCR фото и быстрый текстовый парсер сохраняются; новый слой
  дополняет их, не заменяет.
- Целевой предел голосового цикла — 15 секунд.
- Для этого контура: одна расшифровка, `0` LLM-токенов.
- После изменения остаётся кнопка отмены и возврата к той же карточке.

### 3.4. BOT CRM и BOT client

- Единственный production Always-On запускает защищённый `start_safe.py`.
- После релиза выполняется один штатный перезапуск обоих ботов.
- Оба токена проверяются через Telegram `getMe` и обязаны быть действительными.
- Токены BOT CRM и BOT client обязаны различаться и не выводятся в журнал,
  отчёт или чат.
- Падение одного процесса не должно приводить к подмене токена другого.

### 3.5. Изоляция от сайта

- Релиз не изменяет `/site`, `/video`, HTML, карточки сайта или генераторы.
- Патч привязан к хешам только изменяемых функций, поэтому независимые изменения
  дизайна не отменяют фото/голосовой контракт.
- Общая deployment-блокировка исключает одновременную запись с другим релизом.

## 4. Производительность и интерфейс

- Серверный приём фото не ждёт скачивания файла и AI-анализа.
- Слив очереди работает фоном; интерфейс не рисуется на каждое фото.
- CRM-интерфейс функциональный: числа, статусы, короткие ответы, одна следующая
  операция. Декоративный веб-дизайн не участвует в обработке.
- Повторные progress-job не имеют права самостоятельно сливать очередь.

## 5. Безопасная установка

1. Проверить точные хеши целевых функций и текущий контракт fast-path.
2. Снять резервную копию `cars_ui.py`.
3. Получить общую deployment-блокировку.
4. Атомарно заменить только целевые функции.
5. Не менять БД при установке кода.
6. Перезапустить один Always-On `start_safe.py`.
7. Выполнить postcheck.
8. Только после успешного postcheck атомарно восстановить три поля `UA-0011`.
9. При ошибке до подтверждения кода — автоматический rollback и перезапуск.

## 6. Обязательные тесты приёмки

| Тест | Критерий PASS |
|---|---|
| 4 конкурентных обработчика, база 5 + серия 17 | итог 22, серия 17, дублей 0, очередь 0, порядок точный |
| 6 конкурентных обработчиков, серия 100 | итог 100, уникальных 100, очередь 0 |
| Голосовая контрольная фраза | `LPI / 2000 / белый`, три изменения, пропусков 0 |
| Защита карточки | открытая карточка сохраняется, новая не создаётся |
| UA-0011 фото | точных дублей 0; существующие фото не удалены |
| UA-0011 поля | `LPI`, `2000`, `белый` сохранены; остальные поля имеют прежний хеш |
| SQLite | `quick_check=ok`, нет `database is locked` в тесте |
| Боты | CRM `getMe=PASS`, client `getMe=PASS`, токены различаются |
| Изоляция | `site_write=false`, LLM tokens `0` |

## 7. Определение 100% готовности

Задача закрывается только если production-установка имеет статус `PASS`, оба
бота перезапущены и проверены, два фото-теста и голосовой тест прошли, очередь
`UA-0011` равна нулю, точных дублей нет, три поля восстановлены, SQLite цела,
сайт не изменён и машинное доказательство сохранено в GitHub.

## 8. Шкала выполнения

- 0–20%: диагностика и сверка фактов.
- 20–40%: SQLite и долговечная фотоочередь.
- 40–60%: единичный слив, счётчики, голосовой парсер.
- 60–80%: атомарная установка и перезапуск.
- 80–95%: production-тесты и восстановление `UA-0011`.
- 95–100%: фиксация доказательств и итог владельцу.
