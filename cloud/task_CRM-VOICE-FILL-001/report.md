# CRM-VOICE-FILL-001 — Технический отчёт

## Что реализовано

Создан автономный модуль `voice_card_fill.py` (без внешних зависимостей,
без обращения к сети, без записи в `crm.db`), реализующий требуемую
бизнес-логику:

1. **Голос меняет только открытую карточку.** `VoiceCardFillService`
   хранит `active_card[user_id] -> card_id`. Любой голосовой апдейт
   применяется только к этому `card_id`.
2. **Без открытой карточки новая карточка не создаётся.** Если
   `active_card` для пользователя не установлен, метод
   `handle_voice_message` возвращает `status = no_active_card` и не
   вызывает `card_repo.update_card`.
3. **Заполнение пустых полей / изменение только по явному запросу.**
   Поле обновляется, если оно пустое, либо если распознанный текст
   содержит одно из слов-триггеров перезаписи: «измени», «исправь»,
   «замени», «поменяй».
4. **Один вызов распознавания, 0 токенов LLM, лимит 15 секунд.**
   `_transcribe_once` вызывает `transcriber.transcribe(...)` ровно один
   раз на сообщение и явно проверяет, что распознавание уложилось в
   `recognition_timeout_seconds=15`. Извлечение полей выполняется
   детерминированным поиском по ключевым словам (`default_parse_fields`),
   без обращения к LLM.
5. **Повтор одного Telegram-сообщения не пишет повторно.**
   Результат обработки каждого `message_id` кэшируется в
   `_processed_messages`; повторная доставка того же `message_id`
   возвращает закэшированный результат с флагом `deduplicated: True` и
   не вызывает повторный `update_card`.
6. **Отмена последнего голосового изменения.** Каждое успешное
   изменение сохраняет предыдущие значения полей в `_undo_stack`;
   `undo_last(user_id)` восстанавливает их.
7. **Сброс активной карточки при выходе в список/меню.**
   `handle_list_navigation` и `handle_menu_navigation` вызывают
   `reset_active_card`, после чего голос снова требует выбора карточки.

## Тесты

В `tests/test_voice_card_fill.py` — 12 автономных unit-тестов на
фейковых `Transcriber`/`CardRepository` (без реальной БД):

- отсутствие активной карточки не создаёт новую карточку;
- голос обновляет только открытую карточку, вторая карточка не
  затрагивается и общее число карточек не растёт;
- заполненное поле не перезаписывается без ключевого слова;
- заполненное поле перезаписывается при слове «исправь»;
- повторная доставка того же `message_id` не выполняет повторную запись
  и не вызывает второй раз транскрибацию;
- `undo_last` откатывает последнее изменение;
- `undo_last` без истории возвращает `nothing_to_undo`;
- переход в список карточек сбрасывает активную карточку;
- переход в главное меню сбрасывает активную карточку;
- неудачное распознавание возвращает `transcription_failed` и не пишет
  в карточку;
- **acceptance-тест**: «привод передний» в открытой UA-0009 дополняет
  UA-0009 и не увеличивает число карточек — тест
  `test_acceptance_privod_peredniy_does_not_increase_card_count`
  проверяет это напрямую.

Все тесты — офлайн, in-memory, никаких обращений к `crm.db`, сайту или
продакшн-боту.

## Что НЕ сделано в рамках этой поставки (и почему)

- **Реальная интеграция в Telegram-бота и перезапуск бота на
  PythonAnywhere не выполнены.** Правила репозитория прямо запрещают
  Claude/Cloud напрямую трогать продакшн UA ART. Перезапуск бота —
  операционное действие в существующем деплой-пайплайне, а не
  git-коммит в этот репозиторий.
- **Маппинг ключевых слов на реальные поля CRM** (`_DEFAULT_FIELD_KEYWORDS`)
  — это иллюстративный пример для теста acceptance («привод» →
  `drive_type`). Перед реальным подключением модуля к боту маппинг
  нужно свести с фактической схемой полей CRM UA ART (это не требует
  записи в продакшн для выполнения самой проверки соответствия).
- `crm.db`, сайт и карточка UA-0009 не изменялись. Изменения
  затрагивают только код в `cloud/task_CRM-VOICE-FILL-001/`.
