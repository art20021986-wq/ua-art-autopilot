# Восстановление после длительного сбоя — кандидат v8

Статус: **50 локальных и отдельно 50 серверных проверок PASS; рабочая CRM и сайт не изменены**. Это новое изменение после проверенного серверного v7. Его серверный результат 182/182 не распространяется автоматически на v8.

## Найденная причина повторной остановки

В v7 после трёх ошибок обновления страницы задача переходила в `site_sync_status=FAILED`. Обычная сверка повторно ставила только `PASS`, `UNCHANGED` и `NOT_REQUIRED`. Поэтому достаточно длительная временная неисправность могла навсегда остановить автоматическое восстановление этой карточки до ручного повтора.

## Изменение

В v8 сохраняются три попытки в одной серии. После их исчерпания задача сохраняет ошибку и статус `FAILED` на время записанной в SQLite паузы, по умолчанию пять минут. По истечении паузы обычная сверка запускает следующую ограниченную серию только для того же актуального опубликованного автомобиля. Обычное сканирование и повторная инициализация не сокращают эту паузу. Старые `FAILED` без времени следующей проверки получают одну такую паузу при инициализации.

Повтор обновления сайта не запускает заново сбор источников, не меняет его счётчик, значения характеристик, ручные правки или признаки видимости. Скрытие, удаление, смена идентичности, архив удалённых номеров и действующий токен записи продолжают запрещать устаревшую публикацию. Запись статуса использует прежний захват задачи и проверку токена; дополнительного worker нет.

Интервал проверки успешно обработанной страницы по умолчанию уменьшен с 300 до 240 секунд, чтобы оставить запас для обычного опроса. `UA_ART_SPEC_FAILURE_COOLDOWN_SECONDS` ограничен диапазоном 60–300 секунд, стандартное значение 300. Версия этого изменения: `UA-ART-SPEC-AUTO10-RESTORE-V8-SYNC-COOLDOWN`. Версия политики источников сохранена: изменение очереди не должно повторно собирать весь парк.

Существующий срок устаревания захваченной задачи — 1800 секунд — сохранён: уменьшать его без доказанной смерти владельца небезопасно. Для достижения SLA после аварийного завершения процесса остаётся проверить владельца/аренду задания и реальное время серверного цикла с очередью. Политика исчерпания сетевого сбора источников этим изменением не исправлялась.

Сохранённый `/home/Carix/spec_gate_b_restore_20260909/run-20260909T055742431417Z/compiled-candidate` и локальный `private-runtime/candidate-errno22-v7` относятся к v7 и не заменялись. Перед выпуском требуется отдельно собрать новый кандидат, зафиксировать его хеши и проверить v8 в разрешённом стенде. Полный publisher, генератор нового номера и общий Gate B остаются самостоятельными условиями.

Он предназначен только для нового приватного каталога `/home/Carix/spec_retry_v8_20260909` с правами `0700`. Из этого каталога выполняется `python3.10 -I -B retry_gate.py`. Прежний `server_gate.py` не изменён.

В отдельной проверочной копии заменялись только пути и проверка версии Python; этот результат не считается серверным PASS Python 3.10. Фактический серверный отчёт должен появиться в новом `run-*/retry-gate-result.json`.
