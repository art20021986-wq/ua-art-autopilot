# UA-ART-RECOVERY-TASK120-002 v1.0

Техническое задание на контролируемое завершение аварийной остановки TASK120.

Дата: 09.09.2026. Статус: **на утверждение**. Подготовка этого документа ничего не запускает и не меняет. Утверждение ТЗ разрешает анализ, реализацию в отдельном PR и dry-run. Исполнение перехода состояния — только после проверки результата и отдельной команды владельца.

## Причина отдельного задания

В main действует `EMERGENCY_HALT`, оставшийся после неуспешного TASK120. Обычный автоматический запуск блокируется `AUTOMATIC_MODE_HALTED`. Существующий watchdog восстанавливает незавершённую транзакцию, но после отката сам устанавливает HALT; команды снятия остановки в текущем control-plane нет. Шесть текущих транзакций терминальны, поэтому ожидаемое восстановление watchdog не снимет этот стоп. [Control-plane](https://github.com/art20021986-wq/ua-art-autopilot/blob/2ce0c3a886f124c5865c564a7073ef1805861f1c/automation/control_plane.py), [watchdog](https://github.com/art20021986-wq/ua-art-autopilot/blob/2ce0c3a886f124c5865c564a7073ef1805861f1c/.github/workflows/uaart_transaction_watchdog.yml).

Предыдущее согласование UA-ART-SPEC-AUTO-10-RESTORE-001 касается спецификации и оболочки карточки. Настоящее ТЗ добавляет изменение управляющего механизма выпуска, поэтому его предмет вынесен на отдельное утверждение. Повторное согласование уже принятых данных автомобилей не требуется.

## Результат задания

Проверенная штатная процедура, способная завершить **только указанную остановку**, сохранить её историю и подтвердить состояние управления после перехода. Автоматическое снятие любого HALT по факту успешных тестов не допускается. Процедура не публикует автомобили, не восстанавливает production backup и не перезапускает CRM.

## Этап A: подготовка, PR и dry-run

1. Изучить существующие mode, runtime manifest, approvals, transaction/claim/launch/consumed records и очередь. Зафиксировать точный main SHA и хеши всех прочитанных управляющих входов; подтвердить отсутствие незавершённых транзакций и активного production writer.
2. Проверить, какие ожидающие задачи могли бы стартовать после снятия остановки. План должен доказать отсутствие нежелательного запуска старой очереди. Непроверенный запуск, неопределённый активный writer или необходимость дополнительного изменения очереди — `NOT_READY` с конкретной причиной; очередь автоматически не очищается.
3. Подготовить контроллер, тесты и документацию в отдельном PR. Перечень затрагиваемых файлов должен быть явным. Изменения закреплённого runtime проходят его существующие проверки и обновление manifest вместе с проверяемым кодом. Нельзя маскировать несовпадение хешей или отключать валидацию.
4. Контроллер по умолчанию выполняет только dry-run: читает точные входы, выводит их хеши, планируемый переход и полный список допустимых изменений. Сеть и запись в CRM/сайт для dry-run не нужны. Отчёт не содержит секретов, полного VIN или персональных данных.
5. Подготовить результат для владельца: PR/diff, хеш исполняемого кода, хеш dry-run, изолированные тесты, свежая сверка состояния, точный план исполнения и восстановления управляющего стопа при незавершённой операции.

В конце этапа A HALT остаётся действующим. Само слияние подготовительного кода не должно менять режим, удалять стоп или запускать задачи.

## Этап B: отдельное разрешение и контролируемый переход

1. Владелец получает конкретный результат этапа A. Отдельная команда разрешает исполнить этот результат с указанными SHA; одно утверждение настоящего ТЗ не является такой командой.
2. Непосредственно перед переходом повторяются preflight и проверка утверждения. Они связывают HALT, epoch, request/run, reconciliation, main, manifest, очередь и хеш плана. Любой дрейф — отказ без изменений и новый dry-run. Изменение main в процессе подготовки учитывается только новым представленным планом.
3. Используются существующая сериализация production writer и атомарный compare-and-swap по ожидаемому состоянию. Не допускается промежуток, когда HALT снят, а аудит и подтверждение перехода ещё не зафиксированы. Конкретная реализация атомарности и поведения при сбое должна быть доказана тестами до утверждения исполнения.
4. Сохраняются исходные байты HALT, его SHA и все исходные request/claim/transaction/reconciliation/consumed records. Новый неизменяемый recovery receipt связывает их с утверждением, кодом, планом, временем и фактическим исходом. Старая история не редактируется и не заменяется новой версией успеха.
5. Повторное исполнение того же идентификатора не производит вторую запись, повторный запуск или повторный откат. При сбое до фиксации перехода исходный стоп остаётся действующим; неясный исход требует сверки, а не повторения наугад.
6. После фиксации проверяется только ожидаемый результат управления и сохранность всех остальных ограничений. Выдаётся отчёт «управляющая остановка завершена» либо конкретный отказ; это не `Gate B PASS` по спецификации и не подтверждение публикации.

## Сохраняемые ограничения

- Не запускать TASK120 повторно; не сбрасывать его nonce, consumed marker, claim или историю.
- Не публиковать UA-0017/UA-0018, не менять данные/цены/медиа/VIN, HTML и CRM в рамках этого задания.
- Не добавлять права, секреты, production credentials или обходные транспортные маршруты.
- Не применять `allow_halt_for_recovery` к новой предметной production-задаче и не переименовывать её под существующее исключение.
- Не ослаблять Gate B, manifest, exact launch, owner approval, backup, live receipt, pre/post health, ограничения повторов или аварийный стоп при последующих сбоях.
- Не заменять конкретную процедуру глобальным разрешением на снятие будущих остановок.
- Любое дополнительное изменение управления, необходимое по результатам аудита, сначала включить в проверяемый diff и план; исполнять его по умолчанию нельзя.

## Приёмка

На изолированных данных доказать:

| Сценарий | Требуемый результат |
|---|---|
| Точный исходный HALT, подтверждённая история, пустая ожидающая очередь | Dry-run даёт конкретный план; состояние не меняется |
| Нет отдельной команды исполнения или SHA утверждения не совпадает | Отказ без записи |
| Чужие HALT/task/run/epoch/request/reconciliation | Отказ без записи |
| PREPARING, OPEN, ROLLING_BACK либо активный writer | Отказ без записи |
| Непросмотренная ожидающая задача | NOT_READY, без изменения очереди |
| Дрейф между preflight и commit | Compare-and-swap отклоняет переход |
| Сбой до атомарной фиксации | Исходный стоп и история сохранены |
| Успешный переход | Исходная история сохранена; один связанный recovery receipt |
| Повтор того же исполнения | Нет второго перехода или запуска |
| Обычная production-задача после перехода | Все существующие ограничения по-прежнему обязательны |

Окончательная приёмка подготовки требует успешных тестов, проверенного PR, читаемого dry-run и отсутствия незаявленных изменений. Разрешение исполнения фиксируется отдельно. Выпуск спецификации и последующих карточек продолжается только после этого по их предметным проверкам.
