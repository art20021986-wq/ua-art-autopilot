# Установщик данных дополнительной спецификации

`data_install.py` — исполняемая локальная транзакция, а не описание интерфейса. Она предназначена для вызова штатным контроллером в том же процессе и потоке, который уже удерживает настоящий `server_fence.FenceLease`. Сама библиотека не останавливает процессы, не снимает HALT, не открывает publication flock повторно, не закрывает заимствованные fd и не запускает CRM.

## Точный объём

- 32 подготовленных файла: `video/UA-0001.html`…`UA-0016.html` и соответствующие 16 файлов в `site`.
- Создание ранее отсутствовавшей `spec-rebuild.db` с подготовленными 557 сохранёнными характеристиками и 18 записями автомобилей.
- Единственная ячейка действующей CRM: `cars.year` у UA-0016, VIN оканчивается на 1028, опубликована, `1999 → 2017`; закрепляются полные before/after строки и хэши всех 18 строк.
- UA-0017 и UA-0018 остаются черновиками. Закреплены их полные строки и состояние четырёх файлов. Старая база спецификации остаётся неизменной: хэш файла и семантический хэш обеих таблиц, 557 записей в каждой.

Установщик не выполняет свежий сбор десяти источников. Сохранённые характеристики не объявляются заново проверенными.

## Подготовка точного плана

```python
from cloud.spec_rebuild10.data_install import make_manifest, make_install_plan, DataInstall

manifest = make_manifest(snapshot_root, payload_dir)
plan = make_install_plan(
    session, payload_dir, manifest,
    coordination_plan_sha256=reviewed_coordination_plan_sha256,
    fence_sha256=reviewed_server_fence_sha256,
)
```

Обе функции только читают входы. `payload_dir` содержит `spec-rebuild.db` и `candidate/{video,site}/UA-XXXX.html`; текущий подготовленный пакет имеет именно такую структуру. `make_manifest` не пишет `data-manifest.json`: контроллер сохраняет возвращённый объект и план в частный execution package. Полные CRM-строки и VIN в публичный GitHub не помещаются.

Манифест имеет схему `UA-ART-SPEC-REBUILD10-DATA-INSTALL-1`: `scope`, 33 элемента `files` с `before_sha256/after_sha256/mode/payload`, `crm`, `legacy_spec`, `draft_files`, `manifest_sha256`. План связывает манифест с точными session/main/run/nonce/epoch, координационным планом, SHA установщика и SHA настоящего FenceLease. Все SHA JSON считаются через canonical JSON: `ensure_ascii=True`, `sort_keys=True`, компактные разделители; поле собственного SHA исключается.

## Выполнение и проверка

```python
operation = DataInstall(lease, payload_dir, plan, verify_window=trusted_controller.verify_window)
receipt = operation.apply()
current_receipt = operation.read_terminal()
```

`verify_window` обязателен и не имеет положительного значения по умолчанию. На каждую фазу выдаётся новый challenge. Ответ должен быть свежим и связанным с точным планом, содержать независимо подтверждённые разрешение, паузу и завершение **всех** старых писателей, включая WSGI. Локальная подстановка словаря сама по себе доказательством не является. Свежая квота аккаунта проверяется отдельно: предупреждение 70%, запрет тяжёлой установки 80%, аварийный запрет 90%; оценка учитывает фактические исходные файлы, новые файлы, максимальный временный файл, резервную копию CRM и журналы. `statvfs` дополняет квоту, но не заменяет её.

Перед первой заменой сохраняются все исходные HTML с mode/mtime и согласованная SQLite backup CRM. Append-only журнал и файлы синхронизируются через fsync. CRM открывается через `mode=rw`, без смены journal mode, и удерживает `BEGIN IMMEDIATE`. Изменение года остаётся незакоммиченным, пока не записаны и не проверены все 33 файла. SQL commit выполняется последним. Новая база и старая база должны быть без побочных SQLite-файлов; чужой WAL/journal останавливает выполнение. Все исходные файлы и каталоги проверяются на подмену, symlink и hardlink.

`DATA_LOCAL_COMMITTED` означает локальную запись данных и чтение результата. В receipt явно указаны `runtime_loaded_verified=false`, `tasks_resumed=false`, `unpause_authorized=false`, `overall_gate_b=NOT_EVALUATED`. Это не публичная приёмка 16 страниц, не подтверждение загрузки нового CRM-кода и не готовность кнопки UA-0017.

## Возврат и восстановление

`rollback_only()` возвращает только наши версии файлов и нашу ячейку года. Перед первой компенсацией проверяется **весь** набор файлов и все 18 CRM-строк. Любая чужая версия прекращает возврат до перезаписи. Целую CRM поверх чужих изменений метод не восстанавливает. Повторный возврат завершённой операции только проверяет результат.

`finalize_terminal()` закрывает узкое окно сбоя между durable terminal event и записью итогового receipt. Метод заново проверяет фактические данные и разрешение, создаёт только недостающий receipt, не повторяет установку и не меняет прикладные данные.

После фактической смерти процесса держателя нужен **отдельный проверенный recovery-контроллер**, который разрешает восстановление persistent intent и получает новый действующий FenceLease исходной session. `FenceLease.acquire()` намеренно отказывает при старом intent; эта библиотека не удаляет его и не изображает получение полномочий. Новый объект `DataInstall` с восстановленным реальным lease читает тот же план/backup/journal. При оборванной строке журнала метод останавливается для отдельного разбора; он не отбрасывает хвост самостоятельно.

## Исправленная совместимость Python 3.10

Первый реальный серверный прогон на Python3.10.12 выявил 13 ошибок из195:
`set_authorizer(None)` не отключает callback до Python3.11, поэтому последующие
SELECT/ROLLBACK завершались `not authorized`. Исправление сохраняет тот же
ограничивающий callable до закрытия короткоживущего соединения. Запреты на
посторонние UPDATE/INSERT/DELETE/ATTACH/DETACH остаются; разрешены чтение и
завершение транзакции. Добавлены эмуляция прежнего поведения и отдельная
проверка запретов после изменения года. Это исправление совместимости SQLite;
оно не выдаётся за устранение любой исторической ошибки errno22.

## Локальные испытания

```text
PYTHONPATH=rebuild-work:route-work python -m unittest cloud.spec_rebuild10.tests.test_data_install -q
```

Тесты используют настоящий класс FenceLease и шесть существующих lock inode в изолированном каталоге. Проверяют полный 32-страничный/18-строчный цикл, запрет повторного flock, отсутствие полномочий, смену inode и потока, квоту, подмену кандидата, изменения источника и черновиков, отказ при чужих HTML/CRM/WAL, компенсацию частичных замен, прерывание до/после SQL commit, завершение недостающих receipts и запрет повторной установки.

Прерывания внедряются исключением `InstallerInterrupted`, сохраняя живой держатель. Они доказывают восстановление состояния **установщика**, но не работающий маршрут восстановления после гибели серверного держателя. Синтетические ответы verifier существуют только в тестах и не могут считаться Gate B или production receipts. Отдельный прогон на частных настоящих 32 HTML/18 CRM-строках сохраняется контроллером отдельно.

## Переносимый прогон настоящего снимка

```text
python -m cloud.spec_rebuild10.stage_verify --snapshot /stage/snapshot --payload /stage/payload --year-review /stage/year-review.json --output /stage/real-copy-result.json
python -m cloud.spec_rebuild10.stage_verify --selftest --output /stage/selftest-result.json
```

Без `--year-review` используется `payload/year-review.json`. Закреплён SHA ранее проверенных восьми замен года на каждой из двух страниц UA-0016. Прогон всегда сначала копирует приложение в новый временный каталог; к исходному снимку и payload обращается только для чтения. Синтетический verifier помечается в итоговом отчёте. Проверяются все 32 postimage, фактические 557/550/7 характеристики, видимая ссылка и один VIN, точная сохранность оболочки с отдельно разрешёнными заменами года; затем выполняются обратная транзакция и полная сверка 18 CRM-строк. Итог не содержит полных VIN, CRM-строк, частного плана или серверных секретов.

Для переноса нужен весь `cloud/spec_rebuild10`, включая тесты при `--selftest`, и точный `cloud/writer_coordination_001/server_fence.py` в том же Python namespace. Код не содержит абсолютных путей исходного workspace. Во время настоящего прогона исходные данные не переписываются; после проверки временное приложение удаляется. Побайтовый возврат самой `crm.db` не заявляется: SQLite меняет служебный заголовок, поэтому проверяются все логические строки, а полный файл CRM поверх данных никогда не восстанавливается.
