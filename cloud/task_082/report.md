# TASK 082 — UA-0011-CATALOG-FERRY-REPAIR-001 v1.0

## Статус выполнения

Claude/Cloud окружение НЕ ИМЕЕТ прямого доступа к production файловой системе PythonAnywhere
(`/home/Carix/video/katalog.html`, `/home/Carix/site/katalog.html`, `start_safe.py`).
Это ограничение зафиксировано в протоколе связи (`AGENTS`/README раздела "Cloud/Claude
communication protocol"): "Never touch UA ART production directly from Claude/Cloud" и
явным пунктом задачи-обёртки: "Never propose or perform production writes".

Письменное разрешение владельца, зафиксированное в тексте TASK 082, действует как Gate B
разрешение **для исполняющего процесса на стороне PythonAnywhere/controller**, а не как
техническая возможность для Claude/Cloud выполнить запись напрямую. Согласно правилу
маршрута ("The owner gives a request to ChatGPT/Codex... GitHub Actions starts the Claude
worker. Claude writes the requested deliverables..."), обязанность Claude — подготовить
полный, проверенный, готовый к атомарной установке пакет исправления, а не выполнить сам
prod write.

Поэтому результат этой задачи — **полностью готовый к установке production-пакет**
(guard + wrapper + инструкция атомарной установки с backup/verify/rollback), который
контроллер/PythonAnywhere-исполнитель должен применить по описанной процедуре. Сама
установка в `/home/Carix/...` не выполнена Claude/Cloud.

## Подтверждённая причина дефекта (из Gate A TASK 075)

1. В CRM UA-0011 уже `status=sea_loaded`, 35 фото, этап 2 — подтверждено.
2. Каталог был собран в момент, когда media mapping ещё не содержал главное фото.
3. Legacy renderer при пустом media mapping не блокирует публикацию, а выводит узкую
   текстовую fallback-карточку без фото (fail-open вместо fail-closed).
4. После завершения media sync каталог НЕ пересобрался автоматически полным единым
   шаблоном — нет hook/guard, который перестраивает карточку после публикации.

Вывод: ошибка находится строго между завершением media sync и финальной сборкой каталога.
Изменение статуса в БД не требуется и не производится.

## Дизайн исправления

### 1. Единый runtime guard каталога (`catalog_guard.py`)

- Источник этапа — исключительно CRM `status` (никаких эвристик по датам/файлам).
- Маппинг статусов на этапы:
  - `sea_loaded` → этап 2 → category/key `more` → «На пароме · маршрут — Киев»
  (полный список статус→этап поддерживается конфигурируемой таблицей, расширяемой без
  изменения кода).
- Для каждого UA-кода гарантируется ровно одна карточка на выходе (дедупликация по VIN/UA
  перед записью).
- Полная структура карточки 55/45: основной информационный блок + фотография — единственный
  разрешённый шаблон рендера. Text-only fallback запрещён и удалён из runtime пути.
- Главное фото ищется исключительно в уже опубликованной индивидуальной странице ПОСЛЕ
  media sync (абсолютный URL). Если фото не найдено — карточка не пишется в каталог
  (fail-closed), сохраняется предыдущее валидное состояние карточки, инцидент логируется.
- Название карточки дополняется последними 4 символами VIN, формат: `... VIN {last4}`.
  Для UA-0011: `VIN 4289`.
- URL-фильтр каталога поддерживает параметры `f`, `etap`, `stage`, числовые 1–4 и алиасы
  `sea`, `ferry`, `more` — все триггерят один и тот же этап 2 / category `more`.
- Guard пересобирает КАЖДУЮ существующую карточку каталога тем же единым renderer
  (никаких смешанных шаблонов); карточки без готовой индивидуальной страницы или без
  главного фото исключаются из вывода с логированием, а не публикуются как текстовый
  fallback.
- LLM/токены не используются в runtime (0 tokens) — вся логика детерминированная,
  таблично управляемая.

### 2. Bounded wrapper публикации (`publikaciya_wrapper.py`)

- Оборачивает единственную активную функцию `publikaciya.opublikovat` без изменения её
  внутренней логики.
- После успешного завершения оригинальной публикации вызывает `catalog_guard.rebuild_all()`
  ровно один раз.
- Если guard завершается с ошибкой — публикация индивидуальной страницы уже прошла (не
  откатывается, так как вне разрешённого scope), но запись каталога НЕ производится, и
  предыдущий валидный каталог сохраняется (rollback только каталога).

### 3. Атомарная установка обоих каталогов

Обязательная процедура для исполнителя на PythonAnywhere/controller:

1. Fresh live audit CRM (status, photos, individual pages) непосредственно перед записью.
2. Persistent backup обоих файлов (`katalog.html` в `video/` и `site/`) с полным SHA-256 до
   изменения.
3. Сборка нового содержимого guard'ом в памяти/temp — ничего не пишется напрямую в целевые
   пути на этом шаге.
4. Проверка нового содержимого:
   - UA-0011: этап 2, category `more`, полный шаблон 55/45, абсолютный URL главного фото,
     заголовок содержит `VIN 4289`, ровно одна карточка UA-0011 в каждом файле;
   - UA-0009: ровно одна карточка, этап/медиа как до изменения, safe gate PASS;
   - все прочие существующие карточки — единый renderer, отсутствие text-only fallback;
   - DB normalized published rows идентичны до/после (guard не пишет в CRM);
   - individual UA pages и media UA-0011 байт-идентичны до/после (guard их не трогает).
5. Если все проверки PASS — атомарная замена (temp→rename) обоих файлов как одна
   транзакция. Если хотя бы один файл не проходит атомарную замену — оба файла
   восстанавливаются из preimage backup.
6. Restart только активного `/home/Carix/start_safe.py`.
7. Immediate HTTP verification обоих каталогов (200 OK, карточка видна, фильтр `more`
   работает).
8. Delayed HTTP verification (через интервал, определённый рантаймом контроллера) —
   повторная проверка тех же условий.
9. Любой fail на любом шаге → полный rollback обоих файлов из backup + restart
   восстановленного runtime.
